# Technical Discovery

## Product Surface

A responsive, mobile-first public website for Voters, plus a minimal Operator surface (CLI commands and/or a simple admin page). The web client is the only Voter client in the MVP. iOS and Android apps are a planned post-MVP client (see Clients).

## Candidate Stack

- **Backend**: Python, FastAPI. The AI pipeline lives in the same codebase as a reusable module.
- **Frontend**: a React + TypeScript single-page app built with Vite, talking to the FastAPI read-only API; matching runs client-side. See Clients.
- **Storage**: PostgreSQL (SQLite acceptable for local dev). Source Document files on local disk or object storage.
- **PDF text extraction**: `pypdf` (pure Python, BSD-3-Clause, installs on Python 3.15; chosen over PyMuPDF, which ships compiled wheels and is AGPL), with one text string per page. Only `ideology_app.pdf_text` imports it. OCR is out of scope for the MVP: a PDF without a text layer ends `failed`.

## Clients

Decision: React everywhere, web first.

- **Web (MVP)**: React + TypeScript, Vite, React Router, Vitest + Testing Library. A static build (HTML/JS/CSS) with no server rendering.
- **iOS + Android (post-MVP)**: a single React Native app built with Expo, rather than two native apps. The app is small (landing, Questionnaire, results, breakdown, methodology), so native code isn't worth it.
- **What is shared**: shared code is plain TypeScript (domain types, Match Score, Share Link codec, Questionnaire state, API client), not UI components. The web uses semantic HTML and CSS (accessible radio groups, `DESIGN.md` tokens); the mobile app uses React Native components. We chose this over one Expo + `react-native-web` codebase for all three because the MVP is web-only and the web should stay idiomatic, light and accessible. Screens are few, so writing them twice costs little.

Layout: npm workspaces at the repo root, with a committed `package-lock.json`:

```text
packages/core/   # pure TypeScript shared by every client; no React, DOM or platform APIs
  src/domain/          # entities (Statement, Party Position, Answer, Match Score...) and pure rules
  src/application/     # use cases and Questionnaire state, depending only on domain and ports
  src/infrastructure/  # adapters behind the ports: HTTP client for the public API (fetch), Share Link codec
apps/web/        # React web client (MVP)
  src/app/             # composition root: routing, providers, wiring core use cases to adapters
  src/features/        # one folder per user-facing feature (landing, questionnaire, results, share, methodology)
  src/ui/              # presentational components and DESIGN.md tokens; no data fetching
apps/mobile/     # Expo app (post-MVP), same structure as apps/web, reusing packages/core
```

Rules:

- Dependencies point inward: `ui` → `features` → `core/application` → `core/domain`. `core/domain` imports nothing, and `core` never imports React or platform APIs.
- Components hold no business rules. Scoring, encoding and flow state live in `core` and are tested there without a browser.
- Answers live only in client memory and in the Share Link fragment, never in a request.
- Keep it light: no global state library, CSS-in-JS runtime or extra layers unless a feature needs them.

## Data and Storage

- No Voter answers are stored on the server; anonymous feedback text is stored in a separate store (`feedback-api`): only the message, the screen it came from (`landing` / `results`) and the time.
- Share Link: Dataset Version id plus compactly encoded Answers placed in the URL **fragment** (`#…`), so it isn't sent to the server or recorded in access logs.
- Dataset Versions are immutable and kept indefinitely.
- One SQLite database for all Elections is committed at `data/ideology.db` (`shared-database`), beside the bundles in `data/elections/<slug>/`. It is the single source of truth for every developer: Elections, Parties, Source Documents, Pipeline Runs with their recorded LLM calls, Statements, Party Positions and Dataset Versions, so run ids, Dataset Version ids and `request_hash` values agree on every machine. It is built from scratch with `ideology db upgrade` + `ideology data import <bundle>` per Election, stays in `delete` journal mode, is tracked as `binary` and is never downgraded. `ideology db check` (read-only) is the safe-to-commit gate. The app never invokes git: the Operator commits and pushes it by hand (see "Shared database" under Integrations).
- Source Text Bundles (`source-text-bundle`): the manifesto text of each Election is committed under `data/elections/<slug>/` (`election.toml` plus one `.md` per Party); PDFs are never committed. Runbook:
  - Add a Party's manifesto: put the PDF anywhere outside `data/`, run `ideology source extract <pdf> --party <SHORT> --out data/elections/<slug>/<file>.md [--url <public PDF URL>]`, list it in `election.toml`, commit both. Without `--url` its Evidence shows the page with no link.
  - Import into any database (fresh or existing): `ideology db upgrade`, then `ideology data import data/elections/<slug>`. It is idempotent; `ideology data check data/elections/<slug>` confirms the database holds exactly the committed text.
  - Once a `.md` is committed, the PDF is no longer needed by anyone (import, generation and Evidence read only the bundle), so a local-only PDF can be discarded.
  - Replace a manifesto: put the new PDF on your machine, run `source extract … --force` over that Party's `.md` (or delete the file and extract again), review the diff, commit it. Every machine's next `data import` registers a replacement Source Document (the old one stays for older Evidence); in `live` that queues a run.
  - Never edit a `.md` by hand: the import refuses a file that is not in canonical form or whose `text_sha256` does not match.
  - Party logos (`party-logos-data`): put the user's file in `data/elections/<slug>/logos/` and declare `logo = "logos/<file>"` on that Party in `election.toml`; commit the files, the manifest and the upgraded/imported `data/ideology.db` together. Importing logos is a bundle write like any other (pull → `data import` → `data check` → `db check` → commit, never while someone is generating); it never queues a run or touches a Dataset Version. A refused file is reported to the user, never edited. Normalisation (only at the user's request, `CONSTRAINTS.md` Party Logos; the 2023 logos were done this way): trim transparent margins (alpha > 8), fit without distortion into a 256x256 transparent PNG with 6% padding, centred, and save as an optimised PNG; no script is committed yet (see `docs/risks-and-open-questions.md`). The web client shows each logo in a fixed white tile with `object-fit: contain` and no extra padding (`party-logos-display`), so the 6% padding is the logo's only margin.
- Constituencies and candidatures (`constituencies-and-candidatures`, ingestion phase 1): the 52 Congreso Constituencies come from INE, "Relación de provincias con sus códigos" (https://www.ine.es/daco/daco42/codmun/cod_provincia.htm, fetched 2026-11-24): two-character codes `01`..`52` (Ceuta `51`, Melilla `52`), the INE name with an inverted article moved to the front (`A Coruña`, `Illes Balears`, `Las Palmas`, `La Rioja`), bilingual names as INE writes them. `src/ideology_app/constituencies.py` is the reference list; migration `0016` seeds the `constituencies` table with its own copy (`ideology constituency list` prints them, no database needed). Manifest format 2 of `election.toml` declares the candidatures and the document scopes; format 1 keeps working exactly as before, and both committed bundles stay format 1 until `e2e-2026-constituencies`. Example:

  ```toml
  format = 2

  [election]
  country = "ES"
  type = "general"
  date = 2026-11-29
  name = "Elecciones generales 2026"

  [candidatures]
  source = "BOE núm. …, de … de 2026: candidaturas proclamadas …"
  url = "https://www.boe.es/…"            # optional

  [[parties]]
  short_name = "PP"
  name = "Partido Popular"
  constituencies = "all"
  logo = "logos/pp.png"                   # optional, as in format 1

  [[parties]]
  short_name = "UPN-PP"
  name = "Unión del Pueblo Navarro"
  constituencies = ["31"]

  [[documents]]
  file = "pp.md"
  parties = ["PP", "UPN-PP"]

  [[documents]]
  file = "upn.md"
  parties = ["UPN-PP"]
  constituencies = ["31"]                 # optional
  ```

  Phase-1 runbook: (1) read the BOE proclamation of the Election's candidatures; (2) write `[candidatures]` (source, url) and one `[[parties]]` per candidature with its Constituencies (`"all"` or INE codes; a regional coalition is its own Party); (3) for each manifesto, `ideology source extract <pdf> --party <one listed Party> --out data/elections/<slug>/<file>.md` (a shared file names one of its Parties in its front matter) and list it in `[[documents]]` with every Party it applies to; (4) `data import` → `data check` → `db check` → commit, following the shared-database cycle below. Rules: a document is stored as one Source Document row per listed Party, sharing the file and its hash; each row's scope is the document's Constituencies (or the Party's when none are declared) intersected with the Party's (D1). A format-2 import reuses an existing Party only when its short name and name are both equal; other candidatures become new Parties; a Party the manifest no longer lists loses its candidatures and keeps its row and documents (D2, legacy-only Party). A current bundle document that the manifest no longer lists for its Party is refused: discarding a manifesto is a phase-2 review decision (`ingestion-ledger`), not a removal from the manifest (D5). `data check` and `db check` report unknown codes (at read time), candidatures and scopes that differ from the manifest, candidatures on unlisted Parties, a `constituencies` table that differs from the seed, and any Constituency with no candidature (D4). Candidature or scope changes alone never queue a run; added or replaced documents do in `live`, as today. D1–D5 are defaults for team review (`docs/risks-and-open-questions.md`).
- Ingestion Ledger (`ingestion-ledger`): each format-2 Election has `data/elections/<slug>/ingestion-ledger.json` beside `election.toml`, committed with the bundle, written only by `ideology ingestion` commands (no database needed) and never edited (L1: JSON with the standard library, canonical bytes `json.dumps(obj, ensure_ascii=False, indent=2) + "\n"`, keys in a fixed order, Parties and documents in manifest order; any other bytes are refused; atomic writes). Shape (ledger format 1): `format`, `election` (the slug), `min_proposals` (N), `parties` (`short_name`, `phase` ∈ `candidature_declared` / `manifesto_reviewed` / `proposals_extracted` / `excluded`, `reason` ∈ `no_manifesto` / `discarded_at_review` / `too_few_proposals` exactly when excluded, `note` only with `no_manifesto`, `proposals` = the summed count), `documents` (`file`, `content_hash`, `parties`, `review` = null or `{decision: kept|discarded, reason: null|no_text_layer|not_a_manifesto|incomplete, note}`, `proposals` only when kept), `conflicts` (ledger format 2, `proposal-conflicts`: one entry per overlap, see "Proposal conflicts" below; a format-1 file is still read with `conflicts: []` and rewritten as format 2 by `ingestion update`). Rules: L2 file only, no database copy (it depends only on the bundle, never on database ids); L3 facts (N, reviews, counts, `no_manifesto`) are stored and the phases are derived from them on every command, which drops stale facts with one printed line each (a changed `content_hash`, a Party or file no longer listed, `no_manifesto` on a Party that now lists a document); the ledger is up to date when its bytes equal what `update` would write; a missing file means no decision yet (not a check problem, but phase 4 is blocked); L4 review is per document: a Party is Excluded `discarded_at_review` only when every document it lists is discarded, otherwise it goes on with its kept documents and only those count toward N; L5 a review and a count belong to a file and its bytes, a document shared by several Parties is reviewed once; L6 a Party with no `[[documents]]` is pending until `ingestion no-manifesto` records it (refused while it lists a document, cleared automatically once it does; `--undo`); L7 N lives in the file (30 when created, changed only by `update --min-proposals N`, 1..1000), a Party is `proposals_extracted` when every kept document is counted and the sum is ≥ N, Excluded `too_few_proposals` when below; L8 `data check` and `db check` (format 2 only) report an invalid or out-of-date ledger as `Error:` lines (exit 1), pending Parties are not problems, format-1 bundles never have their ledger read. The commands never queue or run a Pipeline Run. Phase-2 runbook: `ideology ingestion status data/elections/<slug>` → for each manifesto `ingestion review DIR FILE` (shows pages, pages without text and characters) then `--keep` or `--discard no-text-layer|not-a-manifesto|incomplete [--note T]` → `ingestion no-manifesto DIR SHORT [--note T]` for Parties with no manifesto → `ingestion update DIR` → `data check` → commit. Phase 3 (`proposal-extraction`) records counts through `record_extraction_in_dir`; `ingestion gate DIR` exits 0 only when every Party is Extracted or Excluded and no conflict is pending. A git merge conflict on the file: take one side, then rerun the commands (and `ingestion update`). L4, L6 and L7 are defaults for team review (`docs/risks-and-open-questions.md`).
- Proposal extraction (`proposal-extraction`, phase 3, format 2 only): `ideology proposals extract data/elections/<slug> [--file F] [--max-calls K] [--restart F] [--yes]` asks the configured LLM (`LLM_PROVIDER` / `LLM_MODEL`, through `cli._provider()`) for every concrete measure or commitment of each document the Ingestion Ledger records as `kept`, and stores a Proposal only when its verbatim text starts on its cited page. Proposals and extraction state belong to the document content (`content_hash`, tables `proposal_extractions`, `proposal_extraction_calls`, `proposals`, migration `0017`), so a file shared by several Parties, an unchanged file and the same bytes in another Election are extracted once (P3); a changed file gets a new extraction and the old one stays for older Evidence. It needs an up-to-date ledger (`ingestion update`) and the bundle imported (`data import`); it never reads candidatures or scopes and never queues a Pipeline Run.
  - Chunking (P2): whole consecutive non-blank pages under `[página N]` markers, up to 12,000 characters counting the markers (a page is never sliced; an oversized page is a chunk alone), and every chunk but the last also shows the next non-blank page as `[página N — solo contexto]`. A Proposal cites the page it starts on and may run onto the next page (the `find_quote_miss` rule); one that starts on the context page is dropped as `context_page` because the next chunk extracts it. Not the legacy 40,000: output is verbatim copy and grows with the input, so 12,000 keeps a worst-case call near 5k output tokens, far below `max_tokens` (16,384), and a failed call that `claude_code` retries re-sends less.
  - Prompt: task `proposal_extraction` `v1` (`src/ideology_app/proposals/prompts.py`, its own `ProposalPrompt`, not in the legacy `PROMPT_VERSIONS`; pinned in `tests/test_proposal_prompts.py`). Spanish system text: extract every Proposal (each list point separately, no choosing, summarising or merging; diagnosis only inside the measure's paragraph), copy `text` verbatim (≤ about 1,000 characters, a contiguous span), `page` = where it starts, nothing that starts on the context page, `categories` 1–3 of the 18 catalog keys (main first), `tags` 0–5 free lower-case Spanish tags, empty list for a cover or index. Schema per request: `text` 1..1500 characters, `page` within the request's pages, at most 120 items. Only page text reaches the prompt.
  - Recording and resume: every call is committed as soon as it returns (`proposal_extraction_calls`, keyed by chunk, with `pipeline.checkpoint.request_hash`). A rerun replays recorded calls with zero LLM calls and calls only the missing chunks; finalize (deterministic, one transaction) runs the check and inserts the Proposals, so a crash before it is repaired with zero calls. `--max-calls K` (default 300, P9) stops cleanly (`Stopped after K calls; run again to continue`, exit 0); an `LLMError` stops with exit 1 and keeps the progress. An in-progress extraction is pinned to its provider, model, prompt version and chunk size (P10); a mismatch is refused (`set LLM_PROVIDER/LLM_MODEL to match, or pass --restart F`), and `--restart F` deletes only an in-progress extraction's calls.
  - Check (P1, P5, `CHECK_VERSION = "v1"`), per item in chunk then item order: `context_page`; then `find_quote_miss` against every page (`no_letters`, `other_page` with `found_on`, `not_found`); then `duplicate` (normalised text equal to an earlier kept Proposal of the document). Nothing is repaired or rewritten. The report (counts and dropped items) is stored on the extraction: `ideology proposals list DIR --file F --dropped`.
  - Ledger: after an extraction is complete (or reused), the command records its validated count through `ingestion_ledger.record_extraction_in_dir` when the ledger differs, and prints the Parties' new states; the Party's `proposals_extracted` or `too_few_proposals` state follows from the summed count and N. `ideology proposals status DIR` lists per kept document `file, hash12, state, chunks done/total, validated, ledger` and the count problems; `data check` and `db check` report a ledger count that differs from the stored Proposals (P8), and `db check` lists unfinished extractions as `proposal extraction <hash12>: in_progress, i/n chunks`.
  - Cost estimate (committed 2026 bundle: 12 files, 1,044 PDF pages, 1,033 non-blank, 2.32M characters): 225 calls (PP 15, PSOE 24, VOX 5, Podemos 33, Frente Amplio 33, Junts 33, ERC 19, Adelante Andalucía 21, BNG 16, Compromís 12, EH Bildu 9, SALF 5) and 2.98M input characters with context pages. Input ≈ 1.1M tokens (≈ 0.85M of page text at about 3.5 characters per token plus ≈ 1.2k system tokens × 225); plan for ≈ 1.7M (the 2023 runs measured 1.5× their estimate on `claude_code`). Output ≈ 0.36–0.54M tokens (40–60 % of the text copied as Proposals plus about 2,700–4,000 Proposals × ~35 tokens of JSON), at most about 5k per call. About 2.5–3.5 h of sequential calls on `claude_code` (spread over sittings with `--max-calls`), or roughly $8–12 on `anthropic` at the Sonnet list price of $3 / $15 per M tokens (check before use). Regional manifestos scale it by their pages (+20–40 %). The real drop rate and yield are measured by `e2e-2026-constituencies`.
  - Defaults for team review (`docs/risks-and-open-questions.md`): P1 strict check, no repair; P2 12,000 characters plus one context page; P3 reuse global by content hash, across Elections; P4 a complete extraction is never redone (a prompt bump does not re-extract); P5 exact normalised dedupe only; P6 1–3 categories and 0–5 tags of at most 40 characters; P7 text 1..1500 characters, one contiguous verbatim excerpt; P8 a count mismatch is a `data check` / `db check` error; P9 `--max-calls` 300 per invocation; P10 a resume is pinned, `--restart` is explicit.
  - Phase-3 runbook: `ingestion status DIR` (every manifesto reviewed) → `data import DIR` and `ingestion update DIR` → `proposals extract DIR` (repeat until every document is complete; on the shared database confirm or pass `--yes`, one active writer) → `proposals status DIR` → `ingestion status DIR` / `ingestion gate DIR` → `data check DIR` and `db check` → commit the ledger and `data/ideology.db` together.
- Proposal conflicts (`proposal-conflicts`, format 2 only): two kept documents of the same Party whose scopes intersect (bundle rule `document_scope`) form an **overlap**, derived into the Ingestion Ledger (ledger format 2) with the Party, both files sorted by name, their `content_hash`es, the sorted intersecting Constituencies and `joint` (the file when exactly one of the two lists the Party in its optional `joint_for` manifest key; both or neither → `null`). `ideology conflicts detect DIR [--max-calls K]` (default 300) asks the configured LLM, one topic-catalog category at a time, which Proposals of one document contradict Proposals of the other, and writes the merged result to the ledger after each overlap (never to the database: no migration, no binary DB merges). `ideology conflicts list DIR`, `conflicts show DIR PARTY FILE FILE` and `conflicts decide DIR PARTY --prevails FILE --over FILE --reason TEXT` complete the loop; phase 4 reads Proposals only through `proposals.conflicts.counted_proposals`.
  - Ledger entry (keys in this order): `party`, `files`, `content_hashes`, `constituencies`, `joint`, `check` (`null` or `{provider, model, prompt_version, calls}`), `contradictions` (`[{proposals: [ordinal in files[0], ordinal in files[1]], category, explanation}]`, sorted by the pair, unique), `status` (`unchecked`, `no_contradiction`, `joint_manifesto`, `decided`, `pending`; derived), `prevails`, `reason`. Facts are the check (written only by `record_conflict_check`) and the decision (written only by `decide_conflict`); the reader checks exact keys, files in `documents` and in the Party's list, hashes equal to the documents' hashes, categories from the topic catalog, ordinals up to each document's ledger count, single-line explanations and reasons (≤ 500 characters, reason required for `decided`), status consistency and canonical bytes.
  - Prompt: task `proposal_conflict_check` `v1` (`src/ideology_app/proposals/conflict_prompts.py`, its own frozen prompt; pinned in `tests/test_conflict_prompts.py`). Spanish system text: two lists of Proposals of the same political force on one topic, from documents A and B; report only pairs that cannot both hold (opposite measures, incompatible figures or deadlines), never extra detail, a topic only one side covers, complementary measures or a regional addition; an empty list when there is none. The prompt shows only the category's name and the numbered texts `A1..An` / `B1..Bm`: no Party names, file names or pages. Schema `conflict_list_schema(len_a, len_b)`: ≤ 40 contradictions, `a` 1..len_a, `b` 1..len_b, `explanation` 1..300 characters on one line; `max_tokens = 4096`.
  - Requests and merge (C1, C10): a Proposal goes in the bucket of each of its categories; a bucket is compared only when both sides are non-empty; above 40,000 characters of Proposal text each side is sliced in ordinal order into slices of ≤ 20,000 and every slice pair is a request. Outputs are merged by `(ordinal_a, ordinal_b)`, keeping the first category and explanation, sorted. A document with 0 Proposals gives a check with 0 calls and no contradiction.
  - Detection order and resume (C6, C8): overlaps in ledger order; an Excluded Party's overlap and an already checked one are skipped; an overlap whose documents' Proposals are not both complete is reported (`Error:`, exit 1) and skipped; another overlap with the same hash pair (same order) is copied with 0 calls; `--max-calls` stops before an overlap whose requests do not fit (exit 0, "Stopped before …"); an `LLMError` stops the run with that overlap still unchecked (its calls are lost: the ledger is written per overlap, not per call). Tokens are printed, not stored.
  - Staleness (C5, C7, C11): a content change of either document clears the check and the decision (the changed file's review is cleared too, so the overlap reappears `unchecked` once it is re-reviewed kept); a scope change keeps both and prints `constituencies A -> B`; a newly joint manifesto clears a stored decision; a prompt bump does not re-check; re-deciding overwrites (no undo command).
  - Applied by phase 4 (C2): `set_aside(ledger, party)` maps `(content_hash, ordinal)` of the losing file's contradicting Proposals of every `joint_manifesto` or `decided` overlap to that overlap's Constituencies; `counted_proposals(session, bundle, ledger, party)` returns each kept document's Proposals with the row's `document_scopes` minus those Constituencies (a Proposal left with none is omitted), and refuses while the Party has an unchecked or pending overlap.
  - Gate (C9): `pending_conflicts` lists every `unchecked` or `pending` overlap of a non-Excluded Party (`P: a.md + b.md (28): not checked; run "ideology conflicts detect DIR"` or `…: 3 contradictions; run "ideology conflicts decide DIR P --prevails FILE --over FILE --reason TEXT"`); `ingestion gate` and `require_phase4_ready` stay closed while it is not empty.
  - Cost estimate (assumptions; no real extraction has run): a national manifesto yields about 100–170k characters of Proposal text, a regional one 50–100k; multi-category membership adds about 1.3×, so 200–300k characters per overlap, 20–30 calls of ≤ 40k characters, ≈ 90–135k input tokens (plan ≈ 200k with the 1.5× measured on `claude_code`) and ≈ 5–15k output tokens. 2026 is expected to have 4–8 overlaps (e.g. PSC, UPN-PP, the Sumar regional coalitions), fewer distinct hash pairs: ≈ 80–240 calls, 0.5–1.6M input and 0.05–0.12M output tokens, about $2–7 on `anthropic` at the Sonnet list price ($3 / $15 per M; check before use) or 1–3 h of sequential calls on `claude_code`, spread over sittings with `--max-calls`.
  - Defaults for team review (C1–C11, `docs/risks-and-open-questions.md`): C1 LLM detection per shared category, not "flag every overlap"; C2 a decision sets aside only the losing document's contradicting Proposals, per Party and overlap Constituency; C3 the marker is `joint_for`, exactly one joint file wins automatically, both or neither go to the Operator; C4 joint pairs are checked too; C5 a content change clears the check and the decision, a scope change keeps them; C6 no migration, checks live in the ledger, resume per overlap; C7 a prompt bump does not re-check; C8 an identical hash pair is reused across Parties; C9 unchecked overlaps block phase 4 except an Excluded Party's; C10 40k characters per request, 40 contradictions per call, 300-character explanations; C11 re-deciding overwrites, no undo command.
  - Runbook: every document extracted (`proposals status DIR`) → `ingestion update DIR` → `conflicts detect DIR` (repeat until no overlap is unchecked) → `conflicts list DIR` → for each `pending` overlap `conflicts show DIR PARTY FILE FILE`, then `conflicts decide DIR PARTY --prevails FILE --over FILE --reason TEXT` → `ingestion gate DIR` → commit the ledger.
- Phase 4 (v2 run, `statements-from-proposals`, format 2 only): `ideology pipeline run-v2 data/elections/<slug> [--resume-from R | --reuse-from R] [--fresh] [--yes]` turns the counted Proposals of a format-2 Election into neutral Statements and Proposal-backed Party Positions, writes a `candidate` Dataset Version marked `model_generation = v2` with its per-Constituency rows (Constituency selection, below) and validates it; a passed run is published (K12). The shared-database confirmation, the unfinished-run guard (same generation) and `--resume-from` / `--reuse-from` (v2 source runs only) work as for `pipeline run`.
  - Gate (refused with exit 1 and one `Error:` line per blocker; no run, call or row is written): `require_phase4_ready` (every Party Extracted or Excluded, no unchecked or pending conflict, the ledger up to date), the Election imported, `ledger_count_problems` empty, then `counted_proposals` per Party with phase `proposals_extracted`. `_start_v2` checks the same gate again; a queued run whose gate closed in the meantime ends `failed` with `phase 4 blocked: …`.
  - S1 grouping: each counted Proposal (distinct by id over all non-Excluded Parties) goes into the bucket of its main category; buckets in catalog order; inside a bucket, sorted by tags (casefolded; none last), `content_hash`, ordinal. One `statement_drafts` call per bucket slice groups similar Proposals (either direction) and writes one Statement per group, citing the group's Proposal numbers in `sources` (recorded in `statement_proposals`, citation order). A Proposal may go unused.
  - S2 slices and carry-forward: slices of at most 40,000 characters of Proposal text (a longer Proposal alone); calls per category sequential, each listing the Statements already drafted for it (`S1..Sm`) and accepting `additions` (more sources for `Sk`); at most 25 new Statements per call; asks for about `clamp(ceil(n/12), 3, 25)`. Pool order: category, call, draft.
  - S3 pool and filter: no bound; target 200 or more (about 1 Statement per 12 Proposals; 225–335 for 2,700–4,000 Proposals). Below 200 the CLI warns. A party-blind filter leaves out Context Notes that fail `check_context_note` (`context_invalid`) and exact duplicates (`duplicate`, first kept) before positioning, recorded under `filtered`.
  - S4 positions: per Party (id order) × category with pool Statements (catalog order), one `proposal_positions` call when the Party has counted Proposals carrying that category among their 1–3 categories; the call lists the category's Statements (`[k] text`) and those Proposals (`P1..Pm`, text only); each answer gives `value` −2..2 and 1–5 Evidence numbers (bounded to the Party's own list). Omitted Statement, no Proposal of the category (no call) or no Proposal at all = `no stance`. Over 60,000 characters the Party's Proposals of a category are sliced; a Statement positioned in several slices keeps the first value and the union of Evidence when every slice gives the same side, else `no stance` and a `slice_disagreement`.
  - S5 one Position per Party × Statement; each Evidence row stores the Constituencies where its Proposal counts for the Party (from `counted_proposals`). Handoff to `constituency-selection-validation`: a Position applies in Constituency c only when one of its Evidence Proposals counts in c, otherwise it reads `no stance` there. Parties whose counted Proposals differ between Constituencies are listed in `partial_scope_parties`.
  - S6 storage (migration `0018`): `party_position_proposals (party_position_id → party_positions CASCADE, rank, proposal_id, source_document_id, constituencies)` and `statement_proposals (statement_id → statements CASCADE, rank, proposal_id)`; rank 1 is mirrored into `evidence_source_document_id`, `evidence_quote` (the Proposal text exactly), `evidence_page` and `evidence_url`, so the `evidence_matches_value` CHECK and the v1 readers are unchanged; the category is stored in `statements.topic`.
  - S7 marker: `pipeline_runs.model_generation` and `dataset_versions.model_generation` (`legacy` | `v2`, NOT NULL, default `legacy`, one named CHECK each). S8: no Anchors in v2. S9 (superseded by K12): `PUBLISH_ON_PASS = {legacy: True, v2: True}` (`pipeline/publishing.py`). S10: the legacy `pipeline run` refuses an Election with candidatures; an already queued legacy run of such an Election ends `failed` (`legacy run refused: election has candidatures`). S11: in `live` the trigger queues nothing for an Election with candidatures (format-1 Elections still queue). S12: source Proposals may go either way; a source Party with `no stance` is counted in `source_party_no_stance`, not an error.
  - Prompts (`src/ideology_app/pipeline/v2/prompts.py`, own frozen `V2Prompt`s, not in `PROMPT_VERSIONS`; pinned in `tests/test_v2_prompts.py`): `statement_drafts` `v1` (`max_tokens` 16384; legacy Statement and Context Note rules plus the grouping rules; template with the category's Spanish name, the earlier Statements, the Proposals as `P1. [tags] text`, the target and maximum, the note length range and the evaluative words) and `proposal_positions` `v1` (`max_tokens` 4096; the 5-point scale; explicit Proposals only, opposite direction = disagreement, never from ideology or silence, 1–5 Evidence numbers). No Party name, file name or page reaches either.
  - Validation: `V2_CHECKS = evidence_quotes, evidence_proposals, statement_sources, statement_uniqueness, context_note, constituency_snapshot, constituency_validity, constituency_availability, constituency_order, statement_rewording` (`validation.checks_for`; `statement_rewording` since `statement-rewording`); the four `constituency_*` checks replace coverage, separation, count and topic spread (see Constituency selection).
  - Calls: at most `MAX_V2_CALLS_PER_RUN = 800` planned (drafts exact, positions an upper bound) before any call. Every call is recorded (`pipeline_run_calls`); a `--reuse-from` replay of an identical run makes 0 calls.
  - Cost estimate (assumptions; no real run here): 2,700–4,000 Proposals of about 350 characters (0.93–1.39M characters; regional manifestos add 20–40 %), 15–25 included Parties. `statement_drafts` ≈ 32–45 calls (up to about 57 with regional manifestos), ≈ 0.35–0.6M input and 0.1M output tokens; `proposal_positions` ≈ 210–350 calls of about 5k input tokens, ≈ 1.0–1.75M input and 0.13–0.2M output. Total ≈ 245–410 calls, ≈ 1.4–2.4M input tokens (plan 2.1–3.6M with the 1.5× seen on `claude_code`), 0.23–0.3M output: about $8–12 on `anthropic` at the Sonnet list price (check before use), up to about $15, or 3–5 h of sequential calls on `claude_code`. Measured by `e2e-2026-constituencies`.
  - Runbook: `ingestion gate DIR` exits 0 → (shared database: pull, tell the team) `caffeinate -is env LLM_PROVIDER=claude_code .venv/bin/ideology pipeline run-v2 DIR` (confirm or `--yes`) → on a stop, resume with `--resume-from R` → `pipeline report --run R` (one `statement_selection` line and one `constituencies` line; the 52-row table is `v2-run-inspection`) → `db check` → commit the DB. A passed v2 run is published; to try other minimums, replay with `VALIDATION_V2_MIN_STATEMENTS=… VALIDATION_V2_MIN_PARTY_SIDES=… pipeline run-v2 DIR --reuse-from R` (0 LLM calls).
- Constituency selection (`constituency-selection-validation`, v2 only): a deterministic, AI-free, Party-identical step between `V2Pool` and `_finish_v2` (`pipeline/v2/selection.py`, rules only in `src/ideology_app/constituency_rules.py`). For each of the 52 Constituencies the Dataset Version stores one `dataset_version_constituencies` row (available, or unavailable with its reason and `detail`; n(c) = `valid_statement_count`; `offered_lengths`), the ranked Statements of an available one (`constituency_statements`, ranks 1..n), and a frozen copy of who runs where with each Excluded Party's ledger reason (`dataset_version_candidatures`; migration `0019`, three insert-only tables, no table recreated). Defaults for team review (K1–K12, `docs/risks-and-open-questions.md`):
  - S5 (`effective_value`): a Party's value in c is its Position's value only when one of the Position's Evidence Proposals lists c; otherwise `no stance` there. R(c) = the non-Excluded Parties of the snapshot running in c.
  - K1 validity: valid in c when, among R(c), at least one Party is in favour (+1/+2) and one against (−1/−2). No "at least 3 Parties" rule (`VALIDATION_MIN_STATEMENT_PARTIES` is legacy only). Fewer than 2 Parties: nothing is valid.
  - K2 order: `(-sided_c, -min(favour_c, against_c), statements.position)`, then topic deferral: for each offered length L strictly below n(c), `cap_L = max(1, VALIDATION_MAX_TOPIC_SHARE_PERCENT * L // 100)`; at rank k up to the largest such L, take the first remaining ranked Statement whose topic has fewer than `cap(k)` placed (`cap(k)` = cap of the first such L ≥ k), else the first remaining one. Past it no cap. Every valid Statement is placed, so each length is a prefix.
  - K3 `VALIDATION_V2_MIN_STATEMENTS` (default 10, integer ≥ 1): fewer valid Statements → `too_few_statements`. The briefing suggested 20, but 20 would make `Todas (N)` (only below 20) impossible.
  - K4 `VALIDATION_V2_MIN_PARTY_SIDES` (default 5 = `LOW_COVERAGE_THRESHOLD` of `packages/core` match-score, integer ≥ 1): every Party of R(c) takes a side on at least that many of c's valid Statements (absolute, over the full set), else `low_party_coverage` with the failing Parties in `detail`. Sides within the first offered length are recorded in the report (`first_length_sides`), not enforced.
  - K5 reasons, first that applies: `fewer_than_two_parties` (`{"parties": k}`), `too_few_statements` (`{"statements": n, "minimum": m}`), `low_party_coverage` (`{"parties": [{"party_id", "sides"}], "minimum": k}`). Stored as codes; the UI maps them to Spanish copy later.
  - K6 topic spread only orders; the max topic share per offered length is recorded (`topic_max_share`, percent rounded down). Never a reason, never a failure.
  - K7 a Statement valid in no available Constituency stays in the Dataset Version (Positions and Evidence kept) with no `constituency_statements` row; counted in `valid_nowhere`.
  - K8 no available Constituency → `constituency_availability` fails the run (`no constituency is available`); nothing is published.
  - K9 the snapshot comes from `load_phase4`: `candidatures_by_party` for every Party in phase `proposals_extracted` or `excluded` (matched by short name), and the Excluded reason from `party_states`. Never read live again; `data check` / `db check` never compare it with live candidatures.
  - K10 `OFFERED_LENGTHS = (20, 30, 40, 50)` (code constant): n < 20 → `[n]` (`Todas (N)`), else the lengths ≤ n; unavailable → `[]`.
  - K11 an unavailable Constituency stores no ranked rows; `valid_statement_count` still records n(c).
  - K12 `PUBLISH_ON_PASS[v2] = True`; a v2 publish supersedes the Election's Published version of either generation (run-id order). The `Not published: v2 …` CLI line is gone.
  - Settings and report: `config.ConstituencySettings` (apart from `ValidationSettings`, so legacy runs record the same `validation_settings` as before); a v2 run records both, flat. `statement_selection["constituencies"]` = `{"version": "v2-constituency-1", "settings": {v2_min_statements, v2_min_party_sides, max_topic_share_percent}, "available", "unavailable": [{"code", "reason"}], "valid_nowhere": [pool numbers], "rows": [{"code", "parties", "excluded", "valid", "lengths", "party_sides": [{"party_id", "sides", "first_length_sides"}], "topic_max_share"}]}`; `REPORT_VERSION` stays `v2-pool-1`.
  - Output: `run-v2` prints `Constituencies: 50 available, 2 unavailable (31 fewer_than_two_parties, 51 too_few_statements); 3 statements valid in no available constituency` after the publish line, and `pipeline report` the same as `constituencies: …` (from the tables; `not recorded` without a Dataset Version). `db check` adds `pipeline.v2.dataset_version_problems`: 52 Constituency rows and ≥ 1 candidature row per v2 version, ranks 1..n per available Constituency, no rows for legacy versions.
- Statement Rewording (`statement-rewording`, v2 only; defaults R1–R12 for team review in `docs/risks-and-open-questions.md`): the Operator fixes a confusing v2 Statement without changing its meaning through a file committed beside `election.toml`, never by editing the database.
  - File `data/elections/<slug>/statement-rewordings.toml` (missing = no rewordings; legacy runs and format-1 bundles never read it; `read_bundle`, `data import`, `data check` and the ledger ignore it):
    ```toml
    format = 1

    [[rewordings]]
    ai_text = "texto exacto de la IA"   # the Statement as the AI wrote it (copy from "pipeline statements")
    text = "nueva redacción"            # 1..300 characters, different from ai_text
    reason = "por qué la original confunde"  # 1..500 characters, never sent to the LLM
    ```
    Only `format` (= 1) and `rewordings` at top level, exactly those three string keys per entry, no two entries with the same `ai_text` (compared like Statement uniqueness: case, accents, whitespace and punctuation ignored), at most 100 entries. A bad file stops `run-v2` with one `Error: <path>:entry N: …` line and nothing written.
  - Matching and checks: an entry applies to the kept Statement of the run whose text equals its `ai_text` (normalised). After Party Positions are assigned (on the AI text), each entry is `not_found` (no such Statement), `duplicate` (its text equals another Statement's or an earlier entry's) or gets one `statement_rewording_check` call (`v1`, `max_tokens` 1024; sees the AI text, its Context Note and the new text only): `applied` when equivalent, else `rejected`. Only `applied` changes the text, in the new Dataset Version; the AI text, reason and the judge's explanation are stored in `statement_rewordings` (migration `0020`). No status fails the run. Positions, Evidence and each Constituency's order stay those of the AI text. Voters (the API) see only the final text.
  - Runbook: (1) find the Statement's exact text with `ideology pipeline statements --dataset-version V`; (2) add an entry to `statement-rewordings.toml` and commit it with the bundle; (3) on the shared database, pull and tell the team, then `ideology pipeline run-v2 data/elections/<slug> --reuse-from R` with R the run of the published version: every draft and position call is reused, only one `statement_rewording_check` call per new or edited entry goes to the provider; the CLI prints `Rewordings: statement-rewordings.toml (N entries)` before the run and `Rewordings: A applied, J rejected, D duplicate, F not found` after it, with one `Warning: rewording of "<ai_text>": <status>[: explanation]` line per entry not applied; (4) read `ideology pipeline report --run R2` (`rewordings:` line and table with status, statement, AI text, new text, reason, explanation); (5) a rejected entry needs a different wording (there is no override); (6) `db check`, commit the DB. A replay of the rewording run itself (`--reuse-from R2`) makes 0 calls.
- Public API for v2 Dataset Versions (`public-dataset-api-v2`; defaults A1–A12 for team review in `docs/risks-and-open-questions.md`): the read model is `src/ideology_app/api/queries_v2.py` (SELECT only, no ledger, no `counted_proposals`); routes, bodies and error codes are in `ARCHITECTURE.md` (Public API).
  - Three path-only `GET` routes under `/api/v1/dataset-versions/{id}`: `constituencies` (the 52 rows), `constituencies/{code}` (ranked Statements, R(c) with S5 values and deduplicated Proposal Evidence, Excluded Parties with reasons) and `constituencies/{code}/proposals/{category}` (the Comparador). Cached `public, max-age=86400, immutable` with a strong ETag, like a legacy version by id; no compression, no pagination.
  - A v2 version is never served in the legacy shape (`404 dataset_version_is_v2` on `getDatasetVersion` and `getPublishedDatasetVersion`); the new routes answer `404 dataset_version_is_legacy` for Dataset Versions 1–5, whose bodies stay byte-identical. `ElectionOut.published_dataset_version_generation` tells a client which to call.
  - Storage: migration `0021` adds the insert-only `dataset_version_proposals` (each non-Excluded Party's counted Proposals in counted order with their Constituencies), written by `_finish_v2` from `phase4.parties` (A8), so the Comparador reads a version's frozen set. `db check` reports a legacy version with rows, a v2 version without, and Evidence not frozen with the same Constituencies. The committed `data/ideology.db` was upgraded to `0021` with the pre-existing tables identical.
  - Client: `packages/core` `ConstituencyApi` (`listConstituencies`, `getConstituencyQuestionnaire`, `getConstituencyProposals`) on `createPublicApiClient`, not yet used by the web app.
- Topic catalog (`topic-catalog`): `src/ideology_app/topic_catalog.py` is the source of truth for the 18 topic keys, their Spanish names and their display order. The order comes from CIS estudio nº 3587, "Barómetro de noviembre 2026" (published 23 Nov 2026, fieldwork 10–17 Nov 2026, N = 8.034), Pregunta 6R "¿Cuál es, a su juicio, el principal problema que existe actualmente en España? ¿Y el segundo? ¿Y el tercero?", TOTAL column (sum of the three mentions, % of respondents), from the results PDF https://www.cis.es/documents/d/guest/es3587mar_a-pdf (advance page https://www.cis.es/en/w/avance-de-resultados-del-estudio-3587-bar%C3%B3metro-de-noviembre-2026-). All 55 categories are recorded in tenths (`CIS_6R_TOTALS`); 49 map to one key each and 6 are unmapped (`CIS_6R_UNMAPPED`). Order rule: a topic's rank value is the highest TOTAL among its categories (not the sum), highest first; ties and topics with no category (last) follow the legacy `prompts.TOPICS` order. The web client gets the same catalog from the generated `packages/core/src/domain/topic-catalog.generated.ts`; after editing the Python module regenerate it with `.venv/bin/python -m ideology_app.topic_catalog > packages/core/src/domain/topic-catalog.generated.ts` (`tests/test_topic_catalog.py` fails when they differ). The catalog does not follow newer barometers automatically.

## Integrations

- LLM provider API(s).
- Local Claude Code CLI (`LLM_PROVIDER=claude_code`, `llm-provider-claude-code`): the Operator's own Claude subscription, no API key, local runs only (never a deployment). Runbook:
  1. Once: `claude auth login` with a Claude subscription (`claude auth status` must show `authMethod` `claude.ai`, or set `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`). An API-key login is rejected before the run starts. `claude auth status` does not prove the OAuth token is fresh: in the `e2e-real-2023-election` smoke run it reported `loggedIn`/`claude.ai` while every call got 401 "OAuth access token has expired" (the run failed before any call, `llm_calls` 0). Before a long run, ping it with `claude -p "responde solo: ok"` and re-run `claude auth login` on a 401.
  2. Run: `caffeinate -is env LLM_PROVIDER=claude_code .venv/bin/ideology pipeline run --election N` (optionally `LLM_MODEL=…` and `LLM_CLAUDE_CODE_MAX_WAIT_HOURS=…`).
  3. Keep the process and the machine awake (on AC power, lid open): when the subscription usage limit is hit, the provider prints `claude_code: usage limit reached (task …); waiting until <time> …` on stderr and waits in-process for the reset, then retries the same call. A real 2023 run (9 Parties) is about 168 calls and can take several usage-limit windows.
  4. If the process or the machine dies, or the run ends `failed` halfway (Ctrl-C ends it `failed: interrupted`; a killed run may stay `running`), every LLM call it completed is already recorded (`pipeline-run-checkpoint`). Resume with `ideology pipeline run --election N --resume-from R`: only the missing calls go to the CLI.
- Shared database (`shared-database`): commands run from the repo root with `export DATABASE_URL=sqlite:///data/ideology.db`. Runbook:
  1. Pull code and DB together (`git pull`) with no `ideology` process or web server open on the DB. Pulling or switching branch replaces the file: an open process would keep writing to the old copy, and those writes are lost.
  2. Tell the team you are generating. One active run at a time on the shared DB, for any Election.
  3. `caffeinate -is env LLM_PROVIDER=claude_code .venv/bin/ideology pipeline run --election N`. Confirm the prompt, or pass `--yes`. Use `--resume-from R` when the CLI or `db check` names an unfinished run (the CLI refuses a new run while the Election has one; `--fresh` starts from zero anyway). To re-run after a finished run (one with a Dataset Version, passed or failed), e.g. after a prompt or selection change, use `--reuse-from R`: identical calls of run R (such as every `statement_candidates` call) are reused with zero tokens and only the changed ones go to the provider (`pipeline-coverage-selection`). `statement_candidates` v2 (`pipeline-statement-priority-tiers`) changed that request, so a `--reuse-from` of runs 1–5 reuses no candidate call (and, since the pool bounds also changed, no `generate_statements` or position call either); a replay of a v2 run that only changes Validation settings (lengths, coverage threshold) re-selects at zero LLM cost while the pool bounds stay the same.
  4. To stop (usage limit, end of day), press Ctrl-C once and wait for the process to exit. The run ends `failed: interrupted`.
  5. Run `.venv/bin/ideology db check`. It must print `Safe to commit: yes`.
  6. Commit only the DB (`git add data/ideology.db`), with a message naming the run and `--resume-from R`, then push. Tell the team. During generation the DB commits go on the branch doing the work, merged to `main` by PR.
  7. The next developer starts at step 1 and resumes with `--resume-from R` (or re-runs a finished run with `--reuse-from R`), using the same `LLM_PROVIDER`/`LLM_MODEL` and code revision. The anchors of a `--reuse-from`/`--resume-from` run are those of run R (`pipeline_runs.anchor_dataset_version_id`, `pipeline-statement-clarity-context`); when R recorded none (it ran with no Published version, or before `0014`), the run uses the Election's current Published version, so its `generate_statements` request differs from R's and goes to the provider.
  8. Other writes (`data import` of a new or changed bundle, `db upgrade` after a migration) follow the same pull → write → `db check` → commit → push cycle, never while someone is generating. A PR that adds a migration also upgrades and commits `data/ideology.db` (`tests/test_committed_database.py` fails until it does).
  9. A merge conflict on the DB means the rule was broken. Keep the side with the run that matters (`git checkout --ours|--theirs`), re-run `db upgrade` or `data import` if that side lacks them, and resume. Never try to merge two DB files.
  10. To serve locally: `DATABASE_URL=sqlite:///data/ideology.db .venv/bin/uvicorn ideology_app.main:app` (every Election).
- HTTP fetch for URL-based Source Documents: stdlib `urllib` (`ideology_app.http_fetch`), http/https only, no new dependency.

Runbook (VPS with Coolify, user decision 2026-11-08):

1. Build and check locally: `docker build -t ideology-app .`, then `docker run --rm -p 127.0.0.1:8000:8000 -v ideology-data:/data ideology-app` and open `http://127.0.0.1:8000/`.
2. In Coolify: a new resource from the GitHub repository, build pack Dockerfile, branch `main`, port `8000`. Do not publish the port on the host: only Coolify's proxy may reach it (that is what makes `FORWARDED_ALLOW_IPS=*` safe).
3. Add a persistent volume mounted at `/data`, and the variables above (`ADMIN_USERS`, `LEGAL_HOLDERS` and `LEGAL_CONTACT_EMAIL` as secrets; `LEGAL_NIF` and `LEGAL_ADDRESS` only if they are to be published). The `LEGAL_*` values are read at startup: a change needs a restart, not a rebuild. Values are trimmed; control characters, `<` and `>` are refused. Set `DONATION_URL` (not a secret) once the project's Buy Me a Coffee profile exists; a restart applies it.
4. Domains: `https://ideologiapp.es`, with `www` and `ideologiapp.com` redirecting to it. Coolify's proxy gets the Let's Encrypt certificates once DNS `A` records point at the VPS. TLS is required: the admin cookie is `Secure` off localhost.
5. Leave the proxy's own access log off, so no request line or client IP is recorded anywhere. Confirm it in Coolify (Traefik's access log): the privacy copy on `/legal` says no access log is kept (`legal-privacy-page`).
6. Check after each deploy: `/health` answers 200; the Landing, a Questionnaire, results, a Share Link and `/metodologia` work; `/legal` shows the configured holders and contact (or the "pendiente de publicación" sentences); no request carries Answers; a feedback message survives a redeploy; `/admin` signs in; `Invítanos a un café` shows in the sidebar and drawer, at the end of the results and on `/legal` with the configured profile when `DONATION_URL` is set, and nowhere when it is not (an invalid value shows `Ignoring DONATION_URL: …` in the container log). `GET /api/v1/donation` and `/api/v1/legal-notice` are cached for 60 s (`public, max-age=60`), so after a restart wait a minute or reload without cache before checking the donation link or `/legal`.
7. Backups: copy the feedback store off the server regularly (a consistent copy, not the raw file while it is open): `docker exec <container> python -c "import sqlite3; sqlite3.connect('/data/feedback.db').backup(sqlite3.connect('/data/feedback-backup.db'))"`, then copy `/data/feedback-backup.db` out (`docker cp <container>:/data/feedback-backup.db .`) and delete it from the volume (`docker exec <container> rm /data/feedback-backup.db`), so messages that Operators delete later do not stay on the server in an old copy. Restore by stopping the container and putting the copy back as `/data/feedback.db`.
8. Roll back by redeploying the previous commit; the feedback volume is untouched.
9. Retention (`legal-privacy-page`): `/legal` promises each feedback message is kept at most `FEEDBACK_RETENTION_MONTHS` (12) months, backups included. Each month, delete in `/admin` the messages older than that (filter `Hasta (UTC)` set to today minus 12 months, then `Borrar`), and delete off-server backups older than that. There is no automatic purge.
10. Sign Netcup's data-processing agreement (AVV, Auftragsverarbeitungsvertrag) in its customer panel: the privacy copy names Netcup GmbH as processor.
11. Donations (`donate-buymeacoffee`): the disclosure and `/legal` promise that a donation made on behalf of a political party is refunded. The holder who receives the donations reviews them on Buy Me a Coffee and refunds any identified as made on behalf of a political party there; donors are not verified, so this is a manual review.

## Observability

- A Pipeline Run log: provider, model, prompt version, token/cost estimate, duration, Validation report.
- No per-user analytics. Basic request metrics only, without query strings or fragments.

## Constraints

- GDPR: political opinions are special category data (Art. 9). Keeping answers out of the server avoids processing them.
- Cost: LLM cost per Pipeline Run must be visible; `live` mode cost must be capped.
