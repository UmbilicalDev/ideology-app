## Implementation-Time Questions

- Settled (`live-mode-url-refetch`): URL Source Documents are re-fetched by `ideology source refetch [--election N]` once their last check (or creation) is at least `SOURCE_REFETCH_INTERVAL_HOURS` old (whole hours, default 6), in both Generation Modes; only `live` queues a run. Scheduling the command (cron or container) is deferred to the first deployment feature.
- Settled: the prompts and chunking for Statements and Party Positions. Statements (`pipeline-generate-statements`): map/reduce over chunks of whole pages of at most 40,000 characters (one `statement_candidates` call per chunk, then one `generate_statements` call), at most 200 LLM calls. Party Positions (`pipeline-extract-positions`): per-chunk findings over the same 40,000-character chunks (one `position_findings` call per chunk), then one `party_positions` reduce per Party, at most 300 calls. Since `pipeline-coverage-selection` the reduce returns a Statement Pool (45..60 by default), positions are extracted for the whole pool with the same calls, and deterministic code selects the Questionnaire. Since `pipeline-balanced-statements` the candidates are balanced per Party by `agenda.balance_candidates` (the same quota for every Party) before the reduce. Versions: `statement_candidates` v1, `generate_statements` v4, `position_findings` v3, `party_positions` v2; real-LLM quality is checked only in `e2e-real-2023-election`.
- Settled (`share-link-create`): /resultados#v1-<datasetVersionId>-<one letter per Statement in position order: a–e = −2..2, s = skip, upper case = Important>; new layouts get a new marker and decoders keep old ones; a truncated link fails the Statement-count check.
- Settled: Evidence quote matching (`validation-evidence-quotes`). Normalisation only (case, accents, ligatures, whitespace and punctuation), then an exact substring match; no edit distance. The quote must start on the cited page (it may run onto the next one).
- Settled (`public-dataset-api`): the API emits `value` as an integer −2..+2 or the string `"no_stance"` (from `PartyPosition.engine_value`), exactly what the `packages/core` match-score engine consumes; `evidence` is `null` exactly when `value` is `"no_stance"`. JSON keys are snake_case; the `packages/core` HTTP adapter maps keys to camelCase once at load.
- Settled (`web-client-skeleton`): FastAPI serves the Vite build from `config.web_dist_dir()` (`$WEB_DIST_DIR`, else `apps/web/dist` relative to the current directory; outside the Python package, so setuptools package-data is not involved) through a catch-all `GET` route included last. `/api/…` and `/health…` are never served by the fallback (404 JSON); real files are served (hashed `assets/` immutable, the rest `no-cache`); a missing path with a `.` in its last segment is a 404; anything else gets `index.html` (`no-cache`). `init.sh` runs `npm ci`, type-check, Vitest and `vite build`.
- The container image (first deployment feature, not yet listed) must build the client with `npm ci && npm run build` and set `WEB_DIST_DIR` to where it copies `apps/web/dist`.
- Settled (`web-client-skeleton`): the Match Score engine is `packages/core/src/domain/match-score.ts`, a line-by-line port with the same exports, checks and messages; the 41 `node:test` cases run under Vitest with the same titles, and a 20,000-case differential run against the old `match-score.js` found 0 mismatches before it was deleted.
- Settled (`live-mode-url-refetch`): the per-Party unique content hash is kept. A changed URL becomes a new row and the old row is marked `replaced_by_id`; bytes that another document of the same Party already has are reported as `duplicate` and change nothing.
- A URL that reverts to an earlier version is not applied: the re-fetch reports `duplicate` (the earlier bytes already have a row in the Party) and the newer version stays current. Re-adding the old version needs a decision (e.g. un-replacing the old row). No owner yet.
- Which document is a coalition's joint manifesto: currently the current parsed document with the lowest-id first version (register it first; a re-fetch replacement keeps its predecessor's place). An explicit Operator flag is undecided.
- Settled (`pipeline-verified-findings`): unverifiable findings are filtered on the reduce's output, not its input. Every finding is verified when its `position_findings` call returns; the `party_positions` request still lists all of them (same numbers, same K), so it is byte-identical and recorded calls stay reusable with `--resume-from` / `--reuse-from`; a choice citing an unverifiable finding becomes `no stance`. Trade-off: the model still sees the slipped candidate, so if it picks the slip while a verified candidate for that Statement exists, the Statement is `no stance` rather than the verified alternative.
- Open (user decision): when the reduce cites a discarded finding, should code fall back to another verified candidate with the same Statement and value? It would recover the stance without an LLM call, but code would be choosing Evidence the model did not choose. Not built (`pipeline-verified-findings`).
- Open (user decision): should `/metodologia` say that a quote not found on its page is discarded during extraction (and becomes "sin posición")? The copy changed only 60 → 50 in `pipeline-verified-findings`; a change must follow `CONSTRAINTS.md` "Public Copy".
- Settled (`validation-party-coverage`): a Party below the coverage threshold fails the whole run; Parties are never excluded and nothing is published with a notice.
- Per-Election coverage thresholds (an override mentioned in `technical-discovery.md`) are not built: `VALIDATION_MIN_PARTY_COVERAGE_PERCENT` is one process-wide value. Add a per-Election override only if a real Election needs it.
- Compound-proposition detection (the "single proposition, no and/or" half of domain check 1) is deferred by `validation-questionnaire-shape`: a lexical "y/o" heuristic would fail whole runs on legitimate Spanish Statements ("investigación y desarrollo") and still miss real compounds. Only the prompts require single propositions today. Revisit with real output in `e2e-real-2023-election`.
- Settled (`auto-publish-dataset-version`): publish order is the Pipeline Run id (queue order). A passing run publishes unless the Election's Published version belongs to a run with a higher id; an older passing run never replaces a newer Published version, and its Dataset Version stays `candidate`.
- LLM cost estimate per run: tokens are recorded and shown by `ideology pipeline report`, but there is no price table, so the report prints `cost: not estimated (no price table)`. Deferred by `live-mode-source-change-trigger` to the first deployment feature, before `pipeline run-queued` is scheduled: the trigger spends nothing (it only records a `queued` run); spending happens only when the Operator runs `run-queued`, bounded by the per-run caps (≤ 200 Statement and ≤ 300 position calls) and by coalescing (≤ 1 queued run per Election).

Workaround: register manifestos with `source add --url`, or give a Source Text file a `source_url` (`source-text-bundle`; the 2023 PSOE and VOX files have none, so their Evidence shows no link). No owner yet.

## Assumptions

- Parties with seats publish a text-based manifesto for each general election.
- An LLM can place parties on Statements reliably enough when it has to cite verbatim Evidence.
- The 2023 general election manifestos are a valid test set until the next election is called (2027 at the latest).

## Risks

- **AI-only accuracy (high).** A wrong Position means a wrong recommendation, with no human in the loop. Mitigations: required Evidence that is verified against the source, automatic Validation, visible quotes, and the provider/model/prompt recorded per run.
- **Perceived bias in Statements (high).** AI-generated wording or topic selection may favour some parties. Mitigations: the topic spread check (enforced since `validation-questionnaire-shape`: no topic above 30% of the Statements by default, `VALIDATION_MAX_TOPIC_SHARE_PERCENT`, and enforced before Validation by the selection's topic cap since `pipeline-coverage-selection`), the separation check, a neutral-wording rule in prompts, the deterministic Statement Selection (no LLM, every Party weighted the same, a Party-relabelling symmetry test, the whole pool and its scores stored on the run and shown by `ideology pipeline report`; see the selection risk below), the public methodology page (`/metodologia`, since `methodology-page`), which states these rules and that the prompts never add party names (the manifesto text itself may contain them), and since `pipeline-balanced-statements` the Party-balanced Agenda: every Party gives the same number of candidates to the reduce whatever its manifesto length (deterministic `agenda.balance_candidates`, a Party-permutation symmetry test), which fixes the agenda-length bias of run 1 (PSOE and SUMAR gave 47 % of the candidates, EH Bildu 1 %). The risk stays open: the wording a real LLM produces is unverified, and a positive-stance bias remains, because stances still come from what manifestos propose (`position_findings` v3 only lets explicit counter-proposals count as disagreement).
- **Evidence links point at a URL's current content (`results-breakdown-evidence`).** A link opens whatever the party's URL serves now. After a re-fetch replaces the document, older Dataset Versions (Share Links, `share-link-open`) may cite a page that no longer matches. Options: serve the stored file of the cited Source Document (see the deferred entry), or a notice when the cited document has been replaced. `share-link-open` makes old Dataset Versions reachable from Share Links but deliberately adds no replaced-document notice (out of its scope, like stored-PDF serving). No owner yet.
- **Re-extracting a PDF with another pypdf version (`source-text-bundle`).** The committed `.md` files are the source of truth, so pypdf version drift matters only when someone runs `ideology source extract` again (e.g. to replace a manifesto). Different extraction then changes the file, the next `data import` replaces that Party's Source Document, and the next run on the shared DB reads the new text. The 2023 bundle was extracted with pypdf 6.21.1, the latest release when extracted (`pypdf>=6.21.1`; it and 6.21.2 reproduce the old DB text exactly, so no `==` pin; a re-extraction with a newer pypdf still changes the `extractor` field and therefore registers a replacement). Mitigation: the `extractor` front-matter field, and comparing the diff before committing a re-extraction.
- **Quote verified but stance misread.** A quote can exist and still not support the assigned value. Validation can't catch this; it can only be detected by the Voter reading the Evidence, which since `results-breakdown-evidence` is one click away on the results screen for every Position. The `party_positions` reduce may also cite a candidate quote that was found for a different Statement, which makes this more likely.
- **Electoral and legal exposure.** Possible scrutiny under electoral rules (LOREG, Junta Electoral Central) close to election day, and claims of misrepresentation. The disclaimer and the methodology page (`/metodologia`) exist since `methodology-page`. Their copy, like the Landing's AI disclosure and methodology summary (`landing-election-picker`), is provisional (comment at the top of `MethodologyPage.tsx`). The legal check of that copy is still open and owned by no feature yet; it must happen before the first public deployment.
- **Non-determinism.** Re-runs yield different Questionnaires; Share Links pin Dataset Versions to contain this. In `live` mode a regeneration after a source change can replace the Questionnaire mid-campaign.
- **Provider cost/availability**, especially in `live` mode. Mitigations since `live-mode-source-change-trigger`: a source change only queues a run (no LLM call, no API key); runs execute only when the Operator runs `ideology pipeline run-queued`; at most one `queued` run per Election however many documents change; per-run call caps. Open: no money cap or price table until the first deployment feature schedules `run-queued`. Since `llm-provider-claude-code`, an Operator run with `LLM_PROVIDER=claude_code` spends no API money (it uses the Operator's Claude subscription) but is bound by the subscription usage limits, so a real run can take many hours (see "Usage limits and multi-hour runs").
- **Runs stuck in `running`.** Ctrl-C now ends a run `failed: interrupted`. A hard kill or crash between a Pipeline Run's commits (after `running`, before the result is recorded) still leaves it in `running`, with no recovery command, so the Operator starts a new run, which can reuse the stuck run's recorded calls with `pipeline run --resume-from` (`pipeline-run-checkpoint`). Since `live-mode-source-change-trigger` the live trigger ignores `running` runs, so a stuck run never blocks queuing, and `pipeline run-queued` touches only `queued` runs. Recovery (marking stale `running` runs `failed`) is deferred to the first deployment feature, the first truly unattended runner. On the committed shared DB (`shared-database`), a `running` row may be a killed run or a run still active on another machine. The CLI cannot tell which, so its guard names both cases and relies on the one-active-run rule. A run left in `validating` (a crash between the Dataset Version commit and Validation, or a run created before `validation-evidence-quotes`) is recoverable with `ideology pipeline validate --run N`, which since `auto-publish-dataset-version` also publishes it when it passes (unless a newer run's version is already Published).
- **Committed shared DB written by two people, or replaced while open (`shared-database`).** A binary DB cannot be merged. If two developers write it at the same time (generating any Election, importing or migrating), or one commits while another's run is writing, one side's calls are lost or paid twice. `git pull` or switching branch while an `ideology` process or the web server has the file open replaces it under the process. SQLite keeps writing to the old copy, and those writes are lost. Mitigations: the one-active-run rule and the CLI confirmation; the runbook (no `ideology` process open during pull, checkout or commit; Ctrl-C and wait for exit before committing); and `ideology db check`, which refuses on `-journal`/`-wal`/`-shm` sidecars, non-`delete` journal mode, a failed integrity check, a schema behind head or a bundle mismatch for any Election with a committed bundle. The committed DB must never be downgraded (see "SQLite downgrades that recreate a table").
- **Concurrent queue executors (first deployment feature).** Two `ideology pipeline run-queued` processes can both start the same `queued` run: `runs._start` reads the status, then updates it, without an atomic claim, on SQLite and PostgreSQL. Run one executor at a time. An atomic `UPDATE … WHERE status = 'queued'` claim is owed by the first deployment feature that schedules `run-queued`.
- **Queued run pinned to an old LLM provider/model (first deployment feature).** A `queued` run keeps the `llm_provider`/`llm_model` recorded when it was queued. After an `LLM_PROVIDER` or `LLM_MODEL` change (switching between `anthropic` and `claude_code` is a provider change), every later live `ideology source add` coalesces onto that old run, and `ideology pipeline run-queued` reports the provider/model mismatch and leaves it `queued`, so the Election never regenerates. The only recovery today is restoring the old settings; there is no cancel or requeue command. Options: a `pipeline cancel --run N` command, coalescing only onto queued runs that match the current provider/model, or having `run-queued` mark such runs `failed`.
- **PostgreSQL publish lock unproven (`e2e-real-2023-election` or the first deployment feature).** `auto-publish-dataset-version` serialises publishers of one Election with `SELECT … FOR UPDATE` on the Election row. CI runs SQLite only, so tests prove the logic, SQLite's write-lock serialisation (threaded test), the partial unique index and that the statement compiles to `FOR UPDATE`, but not real PostgreSQL row-lock behaviour under READ COMMITTED. Prove it with two concurrent `validate_run` calls when PostgreSQL is first deployed. The partial unique index still prevents two Published versions.
- **SQLite busy timeout on concurrent finishers (`auto-publish-dataset-version`).** On SQLite a second `validate_run` waits for the first one's write lock for at most pysqlite's default 5 s busy timeout; after that it ends `failed: unexpected error: OperationalError` with nothing stored, and the Operator re-runs. Only reachable with overlapping runs (`live` mode or two Operator shells).
- **Public API caching (`public-dataset-api`).** Dataset Version bodies are cached for one day as `immutable`, so a serialisation fix or Party-name correction reaches browsers that cached a version only after expiry; the Election list and Published pointer can be 60 s stale after a publish. A feature that lets Party or Election fields change must revisit this.
- **Share Links expose answers to whoever holds them (`share-link-create`).** Anyone with the link sees the Voter's Answers and Important flags, and so can clipboard managers, chat history or any app the link is pasted into. Mitigation: the share note on the end screen says so, and the methodology page says the link is not stored anywhere. The server never sees the fragment. Since `share-link-open` an opened link also stays in the opener's browser history and address bar: the shared page keeps the fragment by design (reload, bookmarks and Back), and its note says the answers travel after «#».
- **Query strings in server access logs (deployment).** The API ignores query strings, but uvicorn's access log records the full request line (seen in the `public-dataset-api` smoke test with `?answers=…`). Since `web-client-skeleton`, `CONSTRAINTS.md` forbids client code from putting Answers in any request (only the URL fragment carries them). The first deployment feature should decide whether to disable or redact access logs.
- **Coalición Canaria excluded from the 2023 Election (user decision, `e2e-real-2023-election`).** The MVP covers "parties with seats", but CCa (1 seat in 2023) is left out on purpose: its only 2023 general-election document is a joint manifesto of about 11 Canarian forces, not its own programme. It is not in the 2023 bundle (`data/elections/es-general-2023-07-23`) or the shared DB, which have 9 Parties after the UPN exclusion below. A Voter who would pick CCa gets no result for it; the methodology page does not mention the exclusion yet (UI copy is out of scope here). Revisit if a CC-only programme turns up or when a feature adds per-Election Party notes.
- **Unión del Pueblo Navarro excluded from the 2023 Election (user decision, `e2e-real-2023-election`).** UPN (1 seat) is left out on purpose: in the `claude_code` smoke run UPN's 6-page programme alone took positions on only 11 of 30 Statements (36%, minimum 70% then; it would still fail at the 50% default since `pipeline-verified-findings`), so it would very likely fail `party_coverage` and with it the whole multi-hour run. This is a user decision about the Party set, not a threshold change. The 2023 bundle and the shared DB have 9 Parties (348 of 350 seats). As with CCa, a Voter gets no result for UPN and the methodology page does not mention it yet. This shows the coverage rule penalises short manifestos (see "Coverage threshold vs real manifestos"); revisit with a per-Party coverage policy or a longer UPN source.
- **Real-LLM behaviour unverified (`e2e-real-2023-election`).** All tests use `FakeProvider`, so none of these have been checked against a real model:
  - prompt quality: neutral wording, single propositions, the topic list;
  - the 40,000-character chunking;
  - the Party Position prompts (`position_findings`, `party_positions`) and whether the 300-call cap fits real manifestos. A run now makes about 2 × chunks + Parties + 1 calls;
  - the model ids `claude-sonnet-5-5` / `claude-haiku-5-5`, and `claude-sonnet-4-6` for `claude_code`;
  - `claude -p` structured output at full scale. The `e2e-real-2023-election` smoke run (scratch DB, UPN alone, `claude_code`/`claude-sonnet-5-5`, 4 calls) observed success envelopes and the model id working; a whole run (about 168 calls) has not been observed.

  Since `pipeline-output-bounds` the request schemas bound the Statement count (since `pipeline-coverage-selection` the pool bounds from `pool_bounds`) and every Statement and evidence number (to the ones listed in that request). With `anthropic`, the SDK (`anthropic>=1.15`, checked on 1.17, `lib/_parse/_transform.py`) sends `minimum`, `maximum`, `maxItems` and a `minItems` above 1 (and `pattern`, lengths) only as hints in the field `description` and validates the answer on the client, so an out-of-range answer fails that call with `LLMOutputError` (no retry) and the run ends `failed` (resumable with `--resume-from`). With `claude_code` the CLI validates against the full schema itself and retries up to 5 times (`error_max_structured_output_retries`), each retry re-sending the chunk and spending usage. Still open: how often a real model breaks the bounds.
- **Usage limits and multi-hour runs (`e2e-real-2023-election`).** With `LLM_PROVIDER=claude_code` (`llm-provider-claude-code`) a usage limit makes the provider wait in-process for the reset and retry. If the machine sleeps hard, the process is killed or the laptop shuts down, the run stops. A weekly limit that resets beyond `LLM_CLAUDE_CODE_MAX_WAIT_HOURS` (default 48) fails the run. Structured output takes at least two model turns per call, so usage per call is higher than the token counts suggest. Mitigation: `caffeinate -is`, AC power, a quiet window. Since `pipeline-run-checkpoint` every successful call is committed as it returns, and `pipeline run --resume-from R` reuses the stopped run's identical calls, so a stop loses at most the call in flight (a killed run still stays `running`; see "Runs stuck in `running`"). Since `shared-database` another developer can resume the run after the DB is committed and pulled (same code revision and `LLM_PROVIDER`/`LLM_MODEL`, or the calls miss or resume is refused).
- **Claude Code CLI output format may change (`llm-provider-claude-code`).** Usage-limit, auth and error detection rely on Claude Code 2.1.110 strings (`You've hit your …`, `You're out of extra usage`, ` · resets <time>`) and fields (`rate_limit_event.rate_limit_info`, `api_error_status`, assistant `error`, `structured_output`). A changed shape fails closed (`LLMProviderError` / `LLMOutputError`, or a 30-minute fallback wait for an unparsable reset), never a silent wrong result. Re-check after CLI upgrades.
- **Quote matching on real manifestos (`e2e-real-2023-election`).** Since `pipeline-verified-findings` extraction checks every finding against its cited page with the `evidence_quotes` matcher, so a copy slip or a page slip by the model drops that one finding (recorded in `statement_selection["findings"]` and shown by `ideology pipeline report`) instead of failing the whole run; `evidence_quotes` stays the final guard. The cost is coverage: a dropped finding cited by the reduce turns that stance into `no stance`. Run 2 (`feature/e2e-real-2023-election-main`, replayed offline with `--reuse-from 2`): 3 of 312 findings dropped (EAJ-PNV 1 of 19, BNG 2 of 30), 2 stances cleared. Still open on real manifestos:
  - extraction errors (wrong characters, interleaved columns) make real quotes fail, and now cost stances;
  - quotes with `…` or `[...]` elisions fail;
  - a quote that crosses a page boundary and copies the chunk's `[página N]` marker fails (one of run 2's BNG drops ends in `[página 41]`);
  - very short quotes (e.g. "no") can match by chance.

  If the drop rate is high, tune the prompts (a new prompt version, which re-runs the calls) or relax to document-level matching. Never edit the output.
- **Coverage threshold vs real manifestos (`e2e-real-2023-election`).** Since `validation-party-coverage` any Party below the coverage threshold (70% until `pipeline-balanced-statements`, then 60%, 50% since `pipeline-verified-findings`) fails the whole run, so one small Party with a short or partial manifesto blocks publishing for every Party. Mitigation: a deliberate threshold change (`VALIDATION_MIN_PARTY_COVERAGE_PERCENT`) or better Source Documents, then a re-run. Never edit the output or drop the Party. Observation (`e2e-real-2023-election` smoke run, 2026-10-21, scratch DB with UPN alone, `claude_code`/`claude-sonnet-5-5`): UPN's 6-page programme took positions on 11 of 30 Statements (36%), far below 70%. With several Parties the Statements differ, but this signalled that UPN (6 pages) and EH Bildu (16 pages) may fail coverage in the real run. User decision: UPN is excluded (entry above); EH Bildu stays, so its coverage is the one to watch in the first fresh run on the shared DB. Observation (run 2 on the shared DB, 2026-10-22): every one of the 9 Parties was below 70% on 35 Statements (EH Bildu 3/35); the loss is in `position_findings` (about 2.3 findings per 40k-character chunk), not in the reduce. Mitigation since `pipeline-coverage-selection`: a 45..60 Statement Pool and a Statement Selection that maximises the worst-covered Party's coverage and picks the largest count in 25..35 that meets the threshold. Observation (the real run on `feature/e2e-real-2023-election-main`, run 1, 2026-10-22): a 58-Statement pool, 26 selected, only ERC at or above 70% (PP 46%, PSOE 58%, VOX 46%, SUMAR 65%, ERC 77%, JUNTS 54%, EH Bildu 46%, EAJ-PNV 46%, BNG 58%); 220 of 522 Statement × Party pairs had a stance and no Statement had all 9 Parties. User decision (2026-10-22, `pipeline-balanced-statements`): the default `VALIDATION_MIN_PARTY_COVERAGE_PERCENT` is lowered from 70 to 60, a deliberate threshold change for every run, not a per-run one; the methodology page says so. The same feature words Statements as orientations most Parties can be placed on and balances the agenda per Party. **EH Bildu has a structural ceiling:** its single 16-page document is one chunk, so it has at most 12 candidates and one `position_findings` call; the quota makes it weigh equally in the agenda, but its coverage still depends on that one call. Observation (run 2 on `feature/e2e-real-2023-election-main`, 168 calls, pool 55, 26 selected): PP 50%, PSOE 73%, VOX 58%, SUMAR 65%, ERC 73%, JUNTS 58%, EH Bildu 50%, EAJ-PNV 50%, BNG 58%, so 6 Parties were below 60%. User decision (2026-10-22, `pipeline-verified-findings`): the default is lowered from 60 to 50, again a deliberate default for every run. An offline `--reuse-from 2` replay with that feature's code (0 LLM calls, all 168 reused) passes with a zero margin: PP, EH Bildu and EAJ-PNV at 13/26 = 50%, so one more lost stance for any of them fails the run, and a fresh (non-replay) run may land below 50%. Open: whether the real replay and later fresh runs reach 50% for every Party (`e2e-real-2023-election`).
- **Separation vs real manifestos (`e2e-real-2023-election`).** Since `validation-statement-separation` any Statement with fewer than two different values among its stances fails the whole run: consensus Statements, and Statements where most Parties have `no stance`. The generation prompt does not see Party Positions. Mitigation since `pipeline-coverage-selection`: the Statement Selection keeps only separating Statements while enough exist (non-separating ones only to reach `min_statements`, which then fails Validation). Mitigation since `pipeline-balanced-statements`: orientation-level Statements (a direction most Parties can be placed on) and a `generate_statements` v4 rule asking for contested axes rather than consensus ones; open until a real run (`e2e-real-2023-election`). Otherwise: re-run, a prompt change or a deliberate threshold (a `ValidationSettings` field). Never drop Statements from a written Dataset Version or edit the output.
- **Questionnaire shape vs real output (`e2e-real-2023-election`).** Since `pipeline-output-bounds` the Statement count is bounded at the `generate_statements` call (the same `ValidationSettings` range, 25..35 by default), so an out-of-range count fails at generation (`LLMOutputError`, resumable), not hours later at Validation; `statement_count` still catches runs validated later with other thresholds. Since `pipeline-coverage-selection` the schema bounds the Statement Pool (`pool_bounds`, 45..60 by default) and the selection keeps the count in the range, leaves out exact duplicates (first in pool order kept) and caps each topic, so these failures reach Validation only when the pool has too few usable Statements. Paraphrased near-duplicates are not caught. On a real model any remaining failure fails the whole run. Mitigation: re-run, a deliberate threshold change (`VALIDATION_MIN_STATEMENTS`, `VALIDATION_MAX_STATEMENTS`, `VALIDATION_MAX_TOPIC_SHARE_PERCENT`) or a prompt change. Never edit the output or drop Statements.
- **Selection shapes the Questionnaire by observed positions (`pipeline-coverage-selection`, high).** The Statement Selection chooses the Questionnaire from what the Parties' manifestos explicitly take a stance on:
  - topics are chosen by where manifestos take explicit stances;
  - since `pipeline-balanced-statements` every Party gives the same number of candidates (long manifestos no longer dominate the pool), but the quota is set by the shortest manifesto (12 candidates for EH Bildu in the 2023 bundle), so the long manifestos are cut down to their first proposals per topic;
  - leximin favours whichever Party is worst covered, which is data-dependent, so that Party's topics gain weight;
  - the separation preference drops consensus topics and favours polarising ones;
  - Validation now partly measures what the selection optimised (coverage, separation, shape).

  Mitigations: identical treatment of Parties (a relabelling symmetry test), no LLM in the selection, the full pool with per-Statement scores and statuses stored on the run (`pipeline_runs.statement_selection`) and shown by `ideology pipeline report`, the public copy on `/metodologia`, and thresholds changed only by deliberate user decision (coverage 50% since `pipeline-verified-findings`, 60% from `pipeline-balanced-statements`). Open: the quality of a real-model pool (owner `e2e-real-2023-election`).
- **Agenda size with a short manifesto (`pipeline-balanced-statements`, `e2e-real-2023-election`).** With quota 12 the reduce sees about 108 candidate lines for a 45..60 pool (run 1's reduce had 934). If the model pads the pool or invents beyond the candidates, revisit `PARTY_QUOTA_MAX` or the floor (`ceil(pool_max / Parties)`) in `pipeline/agenda.py`.
- **Migration `0012` and the run-2 database (`pipeline-coverage-selection`, `e2e-real-2023-election`).** This branch's `data/ideology.db` was upgraded to `0012` with no Pipeline Runs in it; run 2 lives only in the uncommitted `data/ideology.db` of the `e2e-real-2023-election` worktree. When that DB is next committed, keep the side with the run and re-run `ideology db upgrade` on it (runbook step 9); never merge two DB files. Flag it to the orchestrator before merging.
- **Re-fetch operation (`live-mode-url-refetch`, first deployment feature).** Run one `ideology source refetch` at a time: two concurrent processes can download the same document, and only the per-Party unique content hash stops a second replacement (that document is then reported as an error). Replaced Source Document rows and their files are never deleted, so storage grows by one PDF per content change.
- **Operator cleanup gaps.** A Source Document that ends `failed` can't be retried or deleted (`source refetch` does not retry it either); a retry adds a new row. A storage `OSError`, or a trigger failure after `source refetch` stored a replacement file, can leave an orphan content-addressed file (reused on the next try; a trigger failure also records no `last_checked_at`, so the document is retried on every `source refetch`). An unexpected non-`ElectionsError` exception (storage or database error) stops a `source refetch` batch without the "K of M" summary; documents already processed stay committed. Multi-line failure reasons (e.g. a redirect loop) break the tab-separated rows of `ideology source list`. Fine for an MVP CLI; revisit before the Operator workflow gets heavier.
- **Fetching manifests by URL.** There is no host allow-list, so an Operator can point a fetch at a private or loopback address. That's acceptable while fetching is Operator-only via the CLI. Deferred by `live-mode-url-refetch` to whichever feature first accepts URLs from a web or admin surface (no such feature listed yet): `ideology source refetch` re-fetches only URLs an Operator registered with `source add --url`, re-validated before each fetch, and adds no new way to supply a URL. Some party sites block non-browser clients or hide the PDF behind a JavaScript page; those end `failed`, and the Operator can fall back to `--file`. AES-encrypted PDFs are reported as encrypted because `cryptography` isn't installed. History (`e2e-real-2023-election` Phase A, before bundles): psoe.es (Incapsula) and voxespana.es (Cloudflare 403) blocked the fetcher, so PSOE and VOX came from browser downloads (their bundle files have no `source_url`, so their Evidence shows no link), and on one machine the python.org Python 3.15 build had no CA bundle, so `source add --url` failed with `CERTIFICATE_VERIFY_FAILED` unless run with `SSL_CERT_FILE=/etc/ssl/cert.pem` (`http_fetch` uses stdlib `urllib`; the Anthropic SDK uses `truststore` and is unaffected). Since `source-text-bundle` the 2023 text comes from the committed bundle, so neither affects the run. A narrow TLS fix (e.g. a `truststore` SSL context in `http_fetch`) belongs to whichever feature next touches fetching.
- **Parallel branches and migration ids.** Features developed in parallel can both add the same Alembic revision id (e.g. `0004`). Whichever merges second must renumber its revision and its `down_revision` before merging, then re-run `alembic check`.
- **SQLite downgrades that recreate a table.** Migrations run with `PRAGMA foreign_keys=ON`, so a batch downgrade that recreates a table referenced by `ON DELETE CASCADE` deletes every child row. `0003`'s downgrade (recreates `source_documents`) deletes all `source_document_pages` (and would delete Party Positions and run links). `0008` avoids it with a native `DROP COLUMN` (see `CONSTRAINTS.md`). Fix `0003` (or disable foreign keys around batch recreates in `env.py`) before anyone relies on downgrading a database with data; no feature owns it yet. Since `shared-database` the committed `data/ideology.db` is never downgraded; a migration PR upgrades and commits it.
- **Toolchain.** The `.venv` runs Python 3.15, which is very new, so check that new dependencies have wheels for it. `init.sh` requires Node.js ≥ 22.13 (Vite 8, Vitest 5, jsdom 29). npm installs are reproducible (`npm ci` from the committed `package-lock.json`), but there's no Python dependency lockfile, so Python installs aren't. React Router is pinned at `7.18.4` because 8.x needs Node ≥ 22.22 (`landing-election-picker`); move to 8 only together with a deliberate Node floor bump in `init.sh`.

### Accepted Low findings

Not worth fixing now. Fix one when you touch that code anyway.
- Duplicate-party errors don't say whether the name or the short name clashed.
- A `DuplicateError` rolls back the whole session, so batched writes lose earlier rows too.
- The first command on a missing SQLite file creates an empty file, then reports "not initialised". (`shared-database` guards the committed `data/ideology.db` path against this.)
- An explicit `api_key` passed to `AnthropicProvider` is hidden from `repr` but visible through `vars()`.
- `read_pdf_file` checks the size with `stat()` and then reads without a limit.
- URL validation accepts Unicode whitespace (NBSP, U+2028).
- The 60 s fetch timeout applies per socket operation, not per request.
- A body shorter than its `Content-Length` is stored truncated and fails as a PDF.
- In the TypeScript match-score engine (`packages/core`), `lowCoverageThreshold: null` falls back to 5, and `NaN`, `Infinity` and `""` are accepted as Statement ids.
- In the `party_positions` reduce input each candidate quote sits on one line, so a quote containing a newline or `»` makes the input ambiguous (the stored quote is unaffected). Check in `e2e-real-2023-election`.
- When a Party has no stances, `ideology pipeline checks` lists one `statement_separation` entry per Statement (in a two-Party Election, all of them) as well as the one `party_coverage` entry. Intended: checks stay independent, and each separation message names the cause (`only party P has a stance`).
- The Statement duplicate check reuses `normalize_for_match`, which drops separators, so different numbers can collide (`2,1 %` vs `21 %`) and a Statement with no letters or digits normalises to `""`. Both can only cause a false failure, never a false pass.
- Runs that passed before migration `0007` are not backfilled: their Dataset Versions stay `candidate`, and the Operator re-runs to publish (`auto-publish-dataset-version`).
- The Election lock select in `publish_dataset_version` does not use `populate_existing()`, so an `Election` or `DatasetVersion` already loaded in the session could hold stale attributes. Harmless today (the Published-version query filters on database status and `draft` → `active` is idempotent); revisit if more state is read under the lock (`auto-publish-dataset-version`).
- `party_positions.evidence_source_document_id` cascades on Source Document delete, which would remove Party Positions from an immutable Dataset Version. There is no delete path today; revisit before one is added.
- Runs validated before migration `0008` have no recorded thresholds and `ideology pipeline report` shows `validation_settings: not recorded` (no backfill). The report's `duration` covers generation only (`started_at` → `generation_finished_at`); Validation time is shown as its own `validated_at` timestamp, which can be much later when the run was finished with `pipeline validate` (`pipeline-run-report`).
- The public API on a database not migrated to head answers `500` (no `503` or initialisation check per request).
- TypeScript 7 (the native port, `typescript@7.0.2`) may not be supported by tools that need the TypeScript compiler API (typescript-eslint, Expo). A feature that adds one should pin `typescript@6` instead (`web-client-skeleton`).
- The web client catch-all matches before Starlette's trailing-slash redirect, so `/api/v1/elections/` and `/health/` now answer `404 {"detail": "Not Found"}` instead of a `307` to the slash-less path, and `HEAD /` gets `405` (the route is `GET` only). Clients use the exact paths (`web-client-skeleton`).
