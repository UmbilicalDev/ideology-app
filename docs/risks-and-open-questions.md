## Assumptions

## Risks

- **AI-only accuracy (high).** A wrong Position means a wrong recommendation, with no human in the loop. Mitigations: required Evidence that is verified against the source, automatic Validation, visible quotes, and the provider/model/prompt recorded per run.
- **Perceived bias in Statements (high).** AI-generated wording or topic selection may favour some parties. Mitigations: the topic spread check (enforced since `validation-questionnaire-shape`: no topic above 30% of the Statements by default, `VALIDATION_MAX_TOPIC_SHARE_PERCENT`, and enforced before Validation by the selection's topic cap since `pipeline-coverage-selection`), the separation check, a neutral-wording rule in prompts, the deterministic Statement Selection (no LLM, every Party weighted the same, a Party-relabelling symmetry test, the whole pool and its scores stored on the run and shown by `ideology pipeline report`; see the selection risk below), the public methodology page (`/metodologia`, since `methodology-page`), which states these rules and that the prompts never add party names (the manifesto text itself may contain them), and since `pipeline-balanced-statements` the Party-balanced Agenda: every Party gives the same number of candidates to the reduce whatever its manifesto length (deterministic `agenda.balance_candidates`, a Party-permutation symmetry test), which fixes the agenda-length bias of run 1 (PSOE and SUMAR gave 47 % of the candidates, EH Bildu 1 %). The risk stays open: a positive-stance bias remains, because stances still come from what manifestos propose (`position_findings` v3 only lets explicit counter-proposals count as disagreement). Observation (`e2e-real-2023-election` run 3, Dataset Version 3): the 26 Statements' wording reads neutral and orientation-level, phrased in both directions ("Debe derogarse…", "Debe prorrogarse…"), over 17 topics with a maximum topic share of 12% (3 of 26); stances are 104 positive, 29 negative, 0 neutral and 101 no stance (of 234 pairs). One run is not proof, so the entry stays open.
- **Evidence links point at a URL's current content (`results-breakdown-evidence`).** A link opens whatever the party's URL serves now. After a re-fetch replaces the document, older Dataset Versions (Share Links, `share-link-open`) may cite a page that no longer matches. Options: serve the stored file of the cited Source Document (see the deferred entry), or a notice when the cited document has been replaced. `share-link-open` makes old Dataset Versions reachable from Share Links but deliberately adds no replaced-document notice (out of its scope, like stored-PDF serving). No owner yet.
- **Re-extracting a PDF with another pypdf version (`source-text-bundle`).** The committed `.md` files are the source of truth, so pypdf version drift matters only when someone runs `ideology source extract` again (e.g. to replace a manifesto). Different extraction then changes the file, the next `data import` replaces that Party's Source Document, and the next run on the shared DB reads the new text. The 2023 bundle was extracted with pypdf 6.21.1, the latest release when extracted (`pypdf>=6.21.1`; it and 6.21.2 reproduce the old DB text exactly, so no `==` pin; a re-extraction with a newer pypdf still changes the `extractor` field and therefore registers a replacement). Mitigation: the `extractor` front-matter field, and comparing the diff before committing a re-extraction.
- **Quote verified but stance misread.** A quote can exist and still not support the assigned value. Validation can't catch this; it can only be detected by the Voter reading the Evidence, which since `results-breakdown-evidence` is one click away on the results screen for every Position. The `party_positions` reduce may also cite a candidate quote that was found for a different Statement, which makes this more likely. Observation (`e2e-real-2023-election`, reading sample of 10 Positions of Dataset Version 3): of the 9 sampled stances, 1 has an inverted sign (BNG on Statement 26: −2 for a quote that agrees with it), 1 cites a quote about another Statement (PP on Statement 24: wholesale electricity market intervention, not the bank/energy levies) and 1 is weak (PSOE on Statement 2: a general "no derogar las reformas en marcha"); the other 6 support their value, and every quote was verbatim on its cited page. Stays open; no feature owns a fix (options: a prompt change, or a second check of value against quote).
- **Electoral and legal exposure.** Possible scrutiny under electoral rules (LOREG, Junta Electoral Central) close to election day, and claims of misrepresentation. The disclaimer and the methodology page (`/metodologia`) exist since `methodology-page`. Their copy, like the Landing's AI disclosure and methodology summary (`landing-election-picker`), is provisional (comment at the top of `MethodologyPage.tsx`). The legal check of that copy is still open and owned by no feature yet; it must happen before the first public deployment.
- **Non-determinism.** Re-runs yield different Questionnaires; Share Links pin Dataset Versions to contain this. In `live` mode a regeneration after a source change can replace the Questionnaire mid-campaign.
- **Provider cost/availability**, especially in `live` mode. Mitigations since `live-mode-source-change-trigger`: a source change only queues a run (no LLM call, no API key); runs execute only when the Operator runs `ideology pipeline run-queued`; at most one `queued` run per Election however many documents change; per-run call caps. Open: no money cap or price table until the first deployment feature schedules `run-queued`. Since `llm-provider-claude-code`, an Operator run with `LLM_PROVIDER=claude_code` spends no API money (it uses the Operator's Claude subscription) but is bound by the subscription usage limits, so a real run can take many hours (see "Usage limits and multi-hour runs").
- **Runs stuck in `running`.** Ctrl-C now ends a run `failed: interrupted`. A hard kill or crash between a Pipeline Run's commits (after `running`, before the result is recorded) still leaves it in `running`, with no recovery command, so the Operator starts a new run, which can reuse the stuck run's recorded calls with `pipeline run --resume-from` (`pipeline-run-checkpoint`). Since `live-mode-source-change-trigger` the live trigger ignores `running` runs, so a stuck run never blocks queuing, and `pipeline run-queued` touches only `queued` runs. Recovery (marking stale `running` runs `failed`) is deferred to the first deployment feature, the first truly unattended runner. On the committed shared DB (`shared-database`), a `running` row may be a killed run or a run still active on another machine. The CLI cannot tell which, so its guard names both cases and relies on the one-active-run rule. A run left in `validating` (a crash between the Dataset Version commit and Validation, or a run created before `validation-evidence-quotes`) is recoverable with `ideology pipeline validate --run N`, which since `auto-publish-dataset-version` also publishes it when it passes (unless a newer run's version is already Published).
- **Committed shared DB written by two people, or replaced while open (`shared-database`).** A binary DB cannot be merged. If two developers write it at the same time (generating any Election, importing or migrating), or one commits while another's run is writing, one side's calls are lost or paid twice. `git pull` or switching branch while an `ideology` process or the web server has the file open replaces it under the process. SQLite keeps writing to the old copy, and those writes are lost. Mitigations: the one-active-run rule and the CLI confirmation; the runbook (no `ideology` process open during pull, checkout or commit; Ctrl-C and wait for exit before committing); and `ideology db check`, which refuses on `-journal`/`-wal`/`-shm` sidecars, non-`delete` journal mode, a failed integrity check, a schema behind head or a bundle mismatch for any Election with a committed bundle. The committed DB must never be downgraded (see "SQLite downgrades that recreate a table").
- **Concurrent queue executors (first deployment feature).** Two `ideology pipeline run-queued` processes can both start the same `queued` run: `runs._start` reads the status, then updates it, without an atomic claim, on SQLite and PostgreSQL. Run one executor at a time. An atomic `UPDATE … WHERE status = 'queued'` claim is owed by the first deployment feature that schedules `run-queued`.
- **Queued run pinned to an old LLM provider/model (first deployment feature).** A `queued` run keeps the `llm_provider`/`llm_model` recorded when it was queued. After an `LLM_PROVIDER` or `LLM_MODEL` change (switching between `anthropic` and `claude_code` is a provider change), every later live `ideology source add` coalesces onto that old run, and `ideology pipeline run-queued` reports the provider/model mismatch and leaves it `queued`, so the Election never regenerates. The only recovery today is restoring the old settings; there is no cancel or requeue command. Options: a `pipeline cancel --run N` command, coalescing only onto queued runs that match the current provider/model, or having `run-queued` mark such runs `failed`.
- **PostgreSQL publish lock unproven (first deployment feature).** `auto-publish-dataset-version` serialises publishers of one Election with `SELECT … FOR UPDATE` on the Election row. CI runs SQLite only, so tests prove the logic, SQLite's write-lock serialisation (threaded test), the partial unique index and that the statement compiles to `FOR UPDATE`, but not real PostgreSQL row-lock behaviour under READ COMMITTED. Prove it with two concurrent `validate_run` calls when PostgreSQL is first deployed. The partial unique index still prevents two Published versions. Deferred by `e2e-real-2023-election` (SQLite only; no concurrent publishers observed).
- **SQLite busy timeout on concurrent finishers (`auto-publish-dataset-version`).** On SQLite a second `validate_run` waits for the first one's write lock for at most pysqlite's default 5 s busy timeout; after that it ends `failed: unexpected error: OperationalError` with nothing stored, and the Operator re-runs. Only reachable with overlapping runs (`live` mode or two Operator shells).
- **Public API caching (`public-dataset-api`).** Dataset Version bodies are cached for one day as `immutable`, so a serialisation fix or Party-name correction reaches browsers that cached a version only after expiry; the Election list and Published pointer can be 60 s stale after a publish. A feature that lets Party or Election fields change must revisit this.
- **Share Links expose answers to whoever holds them (`share-link-create`).** Anyone with the link sees the Voter's Answers and Important flags, and so can clipboard managers, chat history or any app the link is pasted into. Mitigation: the share note on the end screen says so, and the methodology page says the link is not stored anywhere. The server never sees the fragment. Since `share-link-open` an opened link also stays in the opener's browser history and address bar: the shared page keeps the fragment by design (reload, bookmarks and Back), and its note says the answers travel after «#».
- **Query strings in server access logs (deployment).** The API ignores query strings, but uvicorn's access log records the full request line (seen in the `public-dataset-api` smoke test with `?answers=…`). Since `web-client-skeleton`, `CONSTRAINTS.md` forbids client code from putting Answers in any request (only the URL fragment carries them). The first deployment feature should decide whether to disable or redact access logs.
- **Coalición Canaria excluded from the 2023 Election (user decision, `e2e-real-2023-election`).** The MVP covers "parties with seats", but CCa (1 seat in 2023) is left out on purpose: its only 2023 general-election document is a joint manifesto of about 11 Canarian forces, not its own programme. It is not in the 2023 bundle (`data/elections/es-general-2023-07-23`) or the shared DB, which have 9 Parties after the UPN exclusion below. A Voter who would pick CCa gets no result for it; the methodology page does not mention the exclusion yet (UI copy is out of scope here). Revisit if a CC-only programme turns up or when a feature adds per-Election Party notes.
- **Unión del Pueblo Navarro excluded from the 2023 Election (user decision, `e2e-real-2023-election`).** UPN (1 seat) is left out on purpose: in the `claude_code` smoke run UPN's 6-page programme alone took positions on only 11 of 30 Statements (36%, minimum 70% then; it would still fail at the 50% default since `pipeline-verified-findings`), so it would very likely fail `party_coverage` and with it the whole multi-hour run. This is a user decision about the Party set, not a threshold change. The 2023 bundle and the shared DB have 9 Parties (348 of 350 seats). As with CCa, a Voter gets no result for UPN and the methodology page does not mention it yet. This shows the coverage rule penalises short manifestos (see "Coverage threshold vs real manifestos"); revisit with a per-Party coverage policy or a longer UPN source.
- **Real-LLM behaviour (`e2e-real-2023-election`, observed on runs 1–3).** Tests use `FakeProvider`; the real model was observed once, on the 2023 bundle with `claude_code` / `claude-sonnet-5-5`:
  - the model id `claude-sonnet-5-5` works through `claude -p` (smoke run and runs 1–2); `claude-haiku-5-5` and `claude-sonnet-4-6` were not exercised, nor was `anthropic`;
  - structured output at full scale: 168 calls in run 1 and 89 new calls in run 2, no `LLMOutputError`, no stop and no resume; how often the CLI retried a bound internally is not recorded;
  - chunking and caps: 79 chunks of at most 40,000 characters, 80 Statement calls (cap 200) and 88 position calls (cap 300), as estimated; input tokens per full run were about 3.0–3.1M (estimate about 2.0M), output about 0.11–0.12M;
  - prompt quality: the Dataset Version 3 wording reads as neutral and orientation-level, 17 topics, no topic above 12%; compound Statements and stance quality are covered in their own entries (compound propositions, perceived bias, stance misread).

  Still a risk: one Election, one model and one passing run (a replay) are not proof for other Elections, models or fresh runs.

  Since `pipeline-output-bounds` the request schemas bound the Statement count (since `pipeline-coverage-selection` the pool bounds from `pool_bounds`) and every Statement and evidence number (to the ones listed in that request). With `anthropic`, the SDK (`anthropic>=1.15`, checked on 1.17, `lib/_parse/_transform.py`) sends `minimum`, `maximum`, `maxItems` and a `minItems` above 1 (and `pattern`, lengths) only as hints in the field `description` and validates the answer on the client, so an out-of-range answer fails that call with `LLMOutputError` (no retry) and the run ends `failed` (resumable with `--resume-from`). With `claude_code` the CLI validates against the full schema itself and retries up to 5 times (`error_max_structured_output_retries`), each retry re-sending the chunk and spending usage. On the 2023 runs no call failed with `LLMOutputError`.
- **Usage limits and multi-hour runs (`e2e-real-2023-election`).** With `LLM_PROVIDER=claude_code` (`llm-provider-claude-code`) a usage limit makes the provider wait in-process for the reset and retry. If the machine sleeps hard, the process is killed or the laptop shuts down, the run stops. A weekly limit that resets beyond `LLM_CLAUDE_CODE_MAX_WAIT_HOURS` (default 48) fails the run. Structured output takes at least two model turns per call, so usage per call is higher than the token counts suggest. Mitigation: `caffeinate -is`, AC power, a quiet window. Since `pipeline-run-checkpoint` every successful call is committed as it returns, and `pipeline run --resume-from R` reuses the stopped run's identical calls, so a stop loses at most the call in flight (a killed run still stays `running`; see "Runs stuck in `running`"). Since `shared-database` another developer can resume the run after the DB is committed and pulled (same code revision and `LLM_PROVIDER`/`LLM_MODEL`, or the calls miss or resume is refused). Observation (`e2e-real-2023-election`): run 1 (168 calls) took 901.9 s with no usage-limit wait; run 2 (89 new calls) took 9,390 s including one usage-limit wait handled in-process (resumed on its own, no stop); neither needed `--resume-from`. Keep the mitigations for longer or fresh runs.
- **Claude Code CLI output format may change (`llm-provider-claude-code`).** Usage-limit, auth and error detection rely on Claude Code 2.1.110 strings (`You've hit your …`, `You're out of extra usage`, ` · resets <time>`) and fields (`rate_limit_event.rate_limit_info`, `api_error_status`, assistant `error`, `structured_output`). A changed shape fails closed (`LLMProviderError` / `LLMOutputError`, or a 30-minute fallback wait for an unparsable reset), never a silent wrong result. Re-check after CLI upgrades.
- **Quote matching on real manifestos (`e2e-real-2023-election`).** Since `pipeline-verified-findings` extraction checks every finding against its cited page with the `evidence_quotes` matcher, so a copy slip or a page slip by the model drops that one finding (recorded in `statement_selection["findings"]` and shown by `ideology pipeline report`) instead of failing the whole run; `evidence_quotes` stays the final guard. The cost is coverage: a dropped finding cited by the reduce turns that stance into `no stance`. Observations (`e2e-real-2023-election`): run 1 had 1 failed quote in Validation (VOX p.174, "las" vs "la", a one-letter model slip) and run 2 had 2 (EAJ-PNV, BNG), all model slips, not matching bugs; the cited-page rule held for every other stored quote. In run 3 (the `--reuse-from 2` replay with `pipeline-verified-findings`) 3 of 312 findings were dropped (EAJ-PNV 1 of 19, BNG 2 of 30, all `not_found`), 2 stances cleared, and `evidence_quotes` passed. Of the 133 stored quotes of Dataset Version 3 none uses an elision (`[...]`; one `…` is in the source text), the shortest is 48 characters, and the 10-quote reading sample found every quote verbatim on its page. Still a risk for other manifestos and runs:
  - extraction errors (wrong characters, interleaved columns) make real quotes fail, and now cost stances;
  - quotes with `…` or `[...]` elisions fail;
  - a quote that crosses a page boundary and copies the chunk's `[página N]` marker fails (one of run 2's BNG drops ends in `[página 41]`);
  - very short quotes (e.g. "no") can match by chance.

  If the drop rate is high, tune the prompts (a new prompt version, which re-runs the calls) or relax to document-level matching. Never edit the output.
- **Coverage threshold vs real manifestos (`e2e-real-2023-election`).** Since `validation-party-coverage` any Party below the coverage threshold (70% until `pipeline-balanced-statements`, then 60%, 50% since `pipeline-verified-findings`) fails the whole run, so one small Party with a short or partial manifesto blocks publishing for every Party. Mitigation: a deliberate threshold change (`VALIDATION_MIN_PARTY_COVERAGE_PERCENT`) or better Source Documents, then a re-run. Never edit the output or drop the Party. Observation (`e2e-real-2023-election` smoke run, 2026-10-21, scratch DB with UPN alone, `claude_code`/`claude-sonnet-5-5`): UPN's 6-page programme took positions on 11 of 30 Statements (36%), far below 70%. With several Parties the Statements differ, but this signalled that UPN (6 pages) and EH Bildu (16 pages) may fail coverage in the real run. User decision: UPN is excluded (entry above); EH Bildu stays, so its coverage is the one to watch in the first fresh run on the shared DB. Observation (run 2 on the shared DB, 2026-10-22): every one of the 9 Parties was below 70% on 35 Statements (EH Bildu 3/35); the loss is in `position_findings` (about 2.3 findings per 40k-character chunk), not in the reduce. Mitigation since `pipeline-coverage-selection`: a 45..60 Statement Pool and a Statement Selection that maximises the worst-covered Party's coverage and picks the largest count in 25..35 that meets the threshold. Observation (the real run on `feature/e2e-real-2023-election-main`, run 1, 2026-10-22): a 58-Statement pool, 26 selected, only ERC at or above 70% (PP 46%, PSOE 58%, VOX 46%, SUMAR 65%, ERC 77%, JUNTS 54%, EH Bildu 46%, EAJ-PNV 46%, BNG 58%); 220 of 522 Statement × Party pairs had a stance and no Statement had all 9 Parties. The pool and selection do not fix coverage on their own; the loss is still in `position_findings`. User decision (2026-10-22, `pipeline-balanced-statements`): the default `VALIDATION_MIN_PARTY_COVERAGE_PERCENT` is lowered from 70 to 60, a deliberate threshold change for every run, not a per-run one; the methodology page says so. The same feature words Statements as orientations most Parties can be placed on and balances the agenda per Party. **EH Bildu has a structural ceiling:** its single 16-page document is one chunk, so it has at most 12 candidates and one `position_findings` call; the quota makes it weigh equally in the agenda, but its coverage still depends on that one call. Observation (run 2 on `feature/e2e-real-2023-election-main`, 168 calls, pool 55, 26 selected): PP 50%, PSOE 73%, VOX 58%, SUMAR 65%, ERC 73%, JUNTS 58%, EH Bildu 50%, EAJ-PNV 50%, BNG 58%, so 6 Parties were below 60%. User decision (2026-10-22, `pipeline-verified-findings`): the default is lowered from 60 to 50, again a deliberate default for every run. An offline `--reuse-from 2` replay with that feature's code (0 LLM calls, all 168 reused) passes with a zero margin: PP, EH Bildu and EAJ-PNV at 13/26 = 50%, so one more lost stance for any of them fails the run, and a fresh (non-replay) run may land below 50%. Observation (run 3, the real `--reuse-from 2` replay, 2026-10-22): passed at 50% exactly as projected: PP 13/26, PSOE 18, VOX 14, SUMAR 17, ERC 17, JUNTS 14, EH Bildu 13, EAJ-PNV 13, BNG 14; EH Bildu reached 13 of 26 (16 of the 55-Statement pool) despite its one-chunk ceiling. Remaining risk: zero margin for PP, EH Bildu and EAJ-PNV, so any fresh run (a 2023 re-run or the next Election; no feature owns one yet) may fail coverage. 57% of all Statement × Party pairs had a stance.
- **Separation vs real manifestos (`e2e-real-2023-election`).** Since `validation-statement-separation` any Statement with fewer than two different values among its stances fails the whole run: consensus Statements, and Statements where most Parties have `no stance`. The generation prompt does not see Party Positions. Mitigation since `pipeline-coverage-selection`: the Statement Selection keeps only separating Statements while enough exist (non-separating ones only to reach `min_statements`, which then fails Validation). Mitigation since `pipeline-balanced-statements`: orientation-level Statements (a direction most Parties can be placed on) and a `generate_statements` v4 rule asking for contested axes rather than consensus ones. Observation (`e2e-real-2023-election`): every run passed `statement_separation`; in run 3's 55-Statement pool 9 Statements had a single value (all left out by the selection) and all 26 selected separate (2–4 distinct values). Still a risk for other Elections and fresh runs. Otherwise: re-run, a prompt change or a deliberate threshold (a `ValidationSettings` field). Never drop Statements from a written Dataset Version or edit the output.
- **Questionnaire shape vs real output (`e2e-real-2023-election`).** Since `pipeline-output-bounds` the Statement count is bounded at the `generate_statements` call (the same `ValidationSettings` range, 25..35 by default), so an out-of-range count fails at generation (`LLMOutputError`, resumable), not hours later at Validation; `statement_count` still catches runs validated later with other thresholds. Since `pipeline-coverage-selection` the schema bounds the Statement Pool (`pool_bounds`, 45..60 by default) and the selection keeps the count in the range, leaves out exact duplicates (first in pool order kept) and caps each topic, so these failures reach Validation only when the pool has too few usable Statements. Paraphrased near-duplicates are not caught. On a real model any remaining failure fails the whole run. Observation (`e2e-real-2023-election`): runs 1–3 all passed `statement_count`, `statement_uniqueness` and `topic_spread` (pools 58 and 55, 26 selected each time, largest topic share 3/26 = 12% in run 3); no paraphrased duplicate was noticed in Dataset Version 3. Mitigation: re-run, a deliberate threshold change (`VALIDATION_MIN_STATEMENTS`, `VALIDATION_MAX_STATEMENTS`, `VALIDATION_MAX_TOPIC_SHARE_PERCENT`) or a prompt change. Never edit the output or drop Statements.
- **Selection shapes the Questionnaire by observed positions (`pipeline-coverage-selection`, high).** The Statement Selection chooses the Questionnaire from what the Parties' manifestos explicitly take a stance on:
  - topics are chosen by where manifestos take explicit stances;
  - since `pipeline-balanced-statements` every Party gives the same number of candidates (long manifestos no longer dominate the pool), but the quota is set by the shortest manifesto (12 candidates for EH Bildu in the 2023 bundle), so the long manifestos are cut down to their first proposals per topic;
  - leximin favours whichever Party is worst covered, which is data-dependent, so that Party's topics gain weight;
  - the separation preference drops consensus topics and favours polarising ones;
  - Validation now partly measures what the selection optimised (coverage, separation, shape).

  Mitigations: identical treatment of Parties (a relabelling symmetry test), no LLM in the selection, the full pool with per-Statement scores and statuses stored on the run (`pipeline_runs.statement_selection`) and shown by `ideology pipeline report`, the public copy on `/metodologia`, and thresholds changed only by deliberate user decision (coverage 50% since `pipeline-verified-findings`, 60% from `pipeline-balanced-statements`). Observation (`e2e-real-2023-election` run 3): a 55-Statement pool over 18 topics; the selection left out 29 (9 non-separating, the rest for coverage or the topic cap) and kept 26 over 17 topics, rule `coverage_met`. Readers can audit it with `ideology pipeline report --run 3`. The risk stays: the questionnaire still leans to what manifestos explicitly propose.
- **Agenda size with a short manifesto (`pipeline-balanced-statements`, `e2e-real-2023-election`).** With quota 12 the reduce sees about 108 candidate lines for a 45..60 pool (run 1's reduce had 934). If the model pads the pool or invents beyond the candidates, revisit `PARTY_QUOTA_MAX` or the floor (`ceil(pool_max / Parties)`) in `pipeline/agenda.py`. Observation (`e2e-real-2023-election` runs 2–3): quota 12, 108 lines, every Party 12, and a 55-Statement pool; padding or invention was not measured.
- **Re-fetch operation (`live-mode-url-refetch`, first deployment feature).** Run one `ideology source refetch` at a time: two concurrent processes can download the same document, and only the per-Party unique content hash stops a second replacement (that document is then reported as an error). Replaced Source Document rows and their files are never deleted, so storage grows by one PDF per content change.
- **Operator cleanup gaps.** A Source Document that ends `failed` can't be retried or deleted (`source refetch` does not retry it either); a retry adds a new row. A storage `OSError`, or a trigger failure after `source refetch` stored a replacement file, can leave an orphan content-addressed file (reused on the next try; a trigger failure also records no `last_checked_at`, so the document is retried on every `source refetch`). An unexpected non-`ElectionsError` exception (storage or database error) stops a `source refetch` batch without the "K of M" summary; documents already processed stay committed. Multi-line failure reasons (e.g. a redirect loop) break the tab-separated rows of `ideology source list`. Fine for an MVP CLI; revisit before the Operator workflow gets heavier.
- **Fetching manifests by URL.** There is no host allow-list, so an Operator can point a fetch at a private or loopback address. That's acceptable while fetching is Operator-only via the CLI. Deferred by `live-mode-url-refetch` to whichever feature first accepts URLs from a web or admin surface (no such feature listed yet): `ideology source refetch` re-fetches only URLs an Operator registered with `source add --url`, re-validated before each fetch, and adds no new way to supply a URL. Some party sites block non-browser clients or hide the PDF behind a JavaScript page; those end `failed`, and the Operator can fall back to `--file`. AES-encrypted PDFs are reported as encrypted because `cryptography` isn't installed. History (`e2e-real-2023-election` Phase A, before bundles): psoe.es (Incapsula) and voxespana.es (Cloudflare 403) blocked the fetcher, so PSOE and VOX came from browser downloads (their bundle files have no `source_url`, so their Evidence shows no link), and on one machine the python.org Python 3.15 build had no CA bundle, so `source add --url` failed with `CERTIFICATE_VERIFY_FAILED` unless run with `SSL_CERT_FILE=/etc/ssl/cert.pem` (`http_fetch` uses stdlib `urllib`; the Anthropic SDK uses `truststore` and is unaffected). Since `source-text-bundle` the 2023 text comes from the committed bundle, so neither affects the run. A narrow TLS fix (e.g. a `truststore` SSL context in `http_fetch`) belongs to whichever feature next touches fetching.
- **Parallel branches and migration ids.** Features developed in parallel can both add the same Alembic revision id (e.g. `0004`). Whichever merges second must renumber its revision and its `down_revision` before merging, then re-run `alembic check`.
- **SQLite downgrades that recreate a table.** Migrations run with `PRAGMA foreign_keys=ON`, so a batch downgrade that recreates a table referenced by `ON DELETE CASCADE` deletes every child row. `0003`'s downgrade (recreates `source_documents`) deletes all `source_document_pages` (and would delete Party Positions and run links). `0008` avoids it with a native `DROP COLUMN` (see `CONSTRAINTS.md`). Fix `0003` (or disable foreign keys around batch recreates in `env.py`) before anyone relies on downgrading a database with data; no feature owns it yet. Since `shared-database` the committed `data/ideology.db` is never downgraded; a migration PR upgrades and commits it.
- **Toolchain.** The `.venv` runs Python 3.15, which is very new, so check that new dependencies have wheels for it. `init.sh` requires Node.js ≥ 22.13 (Vite 8, Vitest 5, jsdom 29). npm installs are reproducible (`npm ci` from the committed `package-lock.json`), but there's no Python dependency lockfile, so Python installs aren't. React Router is pinned at `7.18.4` because 8.x needs Node ≥ 22.22 (`landing-election-picker`); move to 8 only together with a deliberate Node floor bump in `init.sh`.
- **Third-party share endpoints (`share-ideologiapp`).** The Comparte IdeologiApp links use `https://www.facebook.com/sharer/sharer.php?u=`, `https://wa.me/?text=` and `https://x.com/intent/post?url=&text=`, which their owners can change or retire without notice. They are only checked by `href` in tests. Check that they still open a prefilled share when the share card is next touched.
- **Brand marks (`share-ideologiapp`).** The Facebook, WhatsApp, Instagram and X glyphs are simplified originals drawn in `currentColor`, not the official assets, and a brand owner could object to their use or look. Revisit before a public launch.

### Accepted Low findings

Not worth fixing now. Fix one when you touch that code anyway.
- Duplicate-party errors don't say whether the name or the short name clashed.
- A `DuplicateError` rolls back the whole session, so batched writes lose earlier rows too.
- The first command on a missing SQLite file creates an empty file, then reports "not initialised". (`shared-database` guards the committed `data/ideology.db` path against this.)
- An explicit `api_key` passed to `AnthropicProvider` is hidden from `repr` but visible through `vars()`.
- `read_pdf_file` checks the size with `stat()` and then reads without a limit.
- URL validation accepts Unicode whitespace (NBSP, U+2028).
- The 60 s fetch timeout applies per socket operation, not per request.
- A body shorter than its `Content-Length` is stored truncated and fails as a PDF.
- In the TypeScript match-score engine (`packages/core`), `lowCoverageThreshold: null` falls back to 5, and `NaN`, `Infinity` and `""` are accepted as Statement ids.
- In the `party_positions` reduce input each candidate quote sits on one line, so a quote containing a newline or `»` makes the input ambiguous (the stored quote is unaffected). Observed in `e2e-real-2023-election`: stored quotes with a newline in Dataset Versions 1/2/3: 21/33/31 (of 129/139/133), with `«` or `»`: 1/0/0; no failure was traced to it (the run 3 replay passed). Kept Low.
- When a Party has no stances, `ideology pipeline checks` lists one `statement_separation` entry per Statement (in a two-Party Election, all of them) as well as the one `party_coverage` entry. Intended: checks stay independent, and each separation message names the cause (`only party P has a stance`).
- The Statement duplicate check reuses `normalize_for_match`, which drops separators, so different numbers can collide (`2,1 %` vs `21 %`) and a Statement with no letters or digits normalises to `""`. Both can only cause a false failure, never a false pass.
- Runs that passed before migration `0007` are not backfilled: their Dataset Versions stay `candidate`, and the Operator re-runs to publish (`auto-publish-dataset-version`).
- The Election lock select in `publish_dataset_version` does not use `populate_existing()`, so an `Election` or `DatasetVersion` already loaded in the session could hold stale attributes. Harmless today (the Published-version query filters on database status and `draft` → `active` is idempotent); revisit if more state is read under the lock (`auto-publish-dataset-version`).
- `party_positions.evidence_source_document_id` cascades on Source Document delete, which would remove Party Positions from an immutable Dataset Version. There is no delete path today; revisit before one is added.
- Runs validated before migration `0008` have no recorded thresholds and `ideology pipeline report` shows `validation_settings: not recorded` (no backfill). The report's `duration` covers generation only (`started_at` → `generation_finished_at`); Validation time is shown as its own `validated_at` timestamp, which can be much later when the run was finished with `pipeline validate` (`pipeline-run-report`).
- The public API on a database not migrated to head answers `500` (no `503` or initialisation check per request).
- TypeScript 7 (the native port, `typescript@7.0.2`) may not be supported by tools that need the TypeScript compiler API (typescript-eslint, Expo). A feature that adds one should pin `typescript@6` instead (`web-client-skeleton`).
- `init.sh`'s closing hint prints `.venv/bin/uvicorn ideology_app.main:app --reload` without `DATABASE_URL`, which serves an empty default `./ideology.db` (`/api/v1/elections` answers `500`), and `init.sh` does not read the `CI` variable that `CI=true ./init.sh` sets. `README.md` explains both; fix the hint when `init.sh` is next touched (`readme`).
- `README.md` troubleshooting says `CERTIFICATE_VERIFY_FAILED` happens only with `source add --url`, but `source refetch` uses the same fetch; and `SSL_CERT_FILE=/etc/ssl/cert.pem` is the macOS path (it may differ on Linux). The README names no tested Linux equivalent of `caffeinate -is` for keeping a long run awake (`readme`).

- Running text uses `max-inline-size: 72ch`; `ch` is the width of a "0", wider than the average Inter letter, so lines can reach about 90 characters. Switch to an `em` measure if long lines are reported (`web-redesign`).
- The custom scale radio returns to the native control under `forced-colors: active`, but no Windows High Contrast check was run (no such environment); re-check when one is available (`material3-civic-horizon-theme`). Under emulated `forced-colors: active` the filled and tonal buttons (`border: 0`) show no boundary; this predates the theme. Fix with `border: 1px solid transparent` or a forced-colors rule.
- `mailto:` share target (`share-ideologiapp`): Correo is a `mailto:` link opened in place; a mail handler registered by a webmail site may open in the same tab in some browsers and lose the in-memory end screen. In the browser check (Claude desktop built-in browser) clicking it left the end screen and its answers in place; in the validator's Google Chrome check it launched the external mail handler and the tab stayed on the end screen.
- Instagram share target on desktop (`share-ideologiapp`): where `navigator.share` exists on desktop, the system share sheet may not offer Instagram. Accepted; the Voter can cancel and use Copiar enlace. The built-in browser has no `navigator.share`, but Google Chrome on macOS does, so desktop Chrome users get the system share sheet; the validator exercised that path with an in-page stand-in, and the real sheet was not opened in either check.
- Accepted Low (`feedback-admin`): the sign-in limiter's global budget (30 attempts per 15 minutes, per process) can be used up by anyone, locking Operators out for up to 15 minutes; a restart clears it. Accepted for two Operators; revisit with the deployment feature (e.g. a proxy-level limit).
- Accepted Low (`feedback-admin`): Operator sign-in has no second factor (no 2FA); the accounts are protected by a 12-character minimum password, scrypt hashes and the rate limit. Revisit if more Operators or more sensitive data are added.
- Accepted Low (`feedback-admin`): the dummy hash used to time unknown-user sign-ins is built lazily, so the first unknown-user attempt after a restart takes about twice as long (~150 ms vs ~77 ms); every later attempt costs the same as a known user. A one-shot hint per process, bounded by the sign-in rate limit. Fix by building `_dummy_hash()` at startup when accounts are configured.
- `ideology feedback list` prints bidi and other format characters (Unicode `Cf`) as stored, so a message can reorder how its own line looks in a terminal. Refusing them would break emoji ZWJ sequences; C0/C1 controls (escape codes) are refused, so nothing can drive the terminal (`feedback-api`).
- The feedback dialog's 429 message says "Espera unos minutos" without reading `Retry-After` (the core client does not expose it); the server window is 600 s (`feedback-dialog`).
- A browser or password-manager autofill could fill the feedback honeypot (`website`), and the real message would then be silently dropped with the normal thank-you. Mitigated by `autoComplete="off"`, `tabIndex=-1` and an unusual label; revisit if reported (`feedback-dialog`).
