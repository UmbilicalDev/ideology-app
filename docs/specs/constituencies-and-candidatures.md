# Feature Implementation Spec: Constituencies, candidatures and document scopes (ingestion phase 1)

## Source Feature

- `id`: constituencies-and-candidatures
- `area`: data
- `depends_on`: v2-domain-docs (accepted)
- `status`: not_started at planning time (2026-11-24)
- `source`: `feature_list.json` (verification: pytest for the migration, the 52-Constituency seed, bundle parsing and import of candidatures and document scopes, and the errors for unknown Constituencies or a Party without Constituencies; `ideology db check` passes on a migrated copy of `data/ideology.db`; `CI=true ./init.sh` passes)
- Branch: `feature/constituencies-and-candidatures`, stacked on `feature/topic-catalog` (PR #124 into `v2`). PR into `v2`, never `main`.
- Owns two Open entries in `docs/risks-and-open-questions.md` "Constituency redesign": (a) candidatures with different names that share a manifesto, and (b) how the 2026 Party rows of Dataset Versions 4–5 map to v2. Both get a default below, marked for team review.

## Goal

Add ingestion phase 1 as data. A migration seeds the 52 Congreso Constituencies. Manifest format 2 of the Source Text Bundle (`election.toml`) lets the Operator declare, per Election, every candidature (Party) with the Constituencies it runs in, from the BOE proclamation, with that source recorded. The Operator also declares which Parties and Constituencies each Source Document applies to. `ideology data import` loads these declarations, and `ideology data check` / `ideology db check` report any divergence, including unknown or missing Constituencies. Format-1 bundles (2023 and 2026) keep importing and checking exactly as they do today. No AI is involved.

## Non-Goals

- Converting the committed 2026 bundle to format 2 or entering the real BOE candidatures. That is Operator data work for `e2e-2026-constituencies`, through `ingestion-guide`. Both committed bundles stay format 1.
- The Ingestion Ledger, manifesto review or discard, Excluded Parties, phase states (`ingestion-ledger`).
- Marking a coalition's joint manifesto, and precedence between documents (`proposal-conflicts`).
- Proposals, the v2 pipeline, per-Constituency Dataset Version data, API or UI (`proposal-extraction`, `statements-from-proposals`, `constituency-selection-validation`, `public-dataset-api-v2`, `constituency-picker`).
- Senado, other countries, search aliases for Constituency names.
- Any change to the Source Text `.md` format (front matter `bundle_format` stays 1) or to `ideology source extract`.
- Any CLI to edit candidatures outside the bundle.

## Job Story

When the BOE has proclaimed an Election's candidatures,
I want to write in one committed manifest which Party runs in which Constituency, and which Constituencies each manifesto covers,
so that every machine imports the same candidatures and the later phases can score Voters only against the Parties on their ballot.

## Users And Permissions

- Operator: edits `election.toml` (format 2), runs `ideology data import|check`, `ideology db upgrade|check`, `ideology constituency list`. Candidatures and scopes are never generated by AI and have no other writer.
- Voter: nothing visible.

## Decisions (defaults for team review, not blocking)

**D1. Shared manifesto, open entry (a).** The rule stays one Party per candidature. A format-2 manifest lists documents separately from Parties. `[[documents]]` names a file, the Parties it applies to (`parties`), and optionally the Constituencies (`constituencies`). The import creates one Source Document row per listed Party. All of these rows share the file, `bundle_file` and `content_hash` (the existing unique constraint is `(party_id, content_hash)`, so this is allowed). Each row gets its own scope: the declared Constituencies, or every Constituency of that Party when none are declared, intersected with that Party's Constituencies. Example: Navarra's `UPN-PP` is its own Party (code 31). `pp.md` lists `parties = ["PP", "UPN-PP"]`, which gives PP's row PP's Constituencies and UPN-PP's row only 31. `upn.md` lists `["UPN-PP"]`. Why one row per Party rather than a document↔Party join table: `source_documents.party_id` is what Evidence, the pipeline, the replacement chain, the live trigger and `check_against_bundle` all key on. Changing it would touch every reader of Dataset Versions 1–5. The cost is that page text is stored once per Party that shares the file. Rejected alternative: listing Party × Constituency pairs per document, which needs 52 lines for each national document and is easy to get wrong.

**D2. Legacy 2026 Party rows, open entry (b).** Party rows are never renamed and never deleted. A format-2 import reuses an existing Party of the same Election only when both `short_name` and `name` are equal, which is the existing matching rule. The reused row gets candidatures in a new table, so its columns stay the same. Every other candidature becomes a new Party row. A legacy row the manifest does not list stays as it is, with no candidatures (a "legacy-only" Party, which v2 features ignore). This is safe for the schema. `party_positions.party_id` points at the rows. `GET` Dataset Version (`api/queries.py` `_version_out`) lists only the Parties with Positions in that version and reads `name`, `short_name` and logo live from `parties`. So new rows never appear in Dataset Versions 4–5, a reused row keeps its name, and Share Links still open those versions. A new Election row is not possible (`elections` is unique on country, type and date), and a parallel Party row with the same name is not possible either (`parties` is unique on election and name, and on election and short name). The bundle stays authoritative for a listed Party's logo, the same rule as today (a logo is not part of a Dataset Version). To keep Dataset Versions 4–5 looking the same, the 2026 format-2 manifest should keep the same logo files for reused Parties.

**D3. Constituency names.** The INE official name, with an inverted article moved to the front: `Coruña, A` → `A Coruña`, `Balears, Illes` → `Illes Balears`, `Palmas, Las` → `Las Palmas`, `Rioja, La` → `La Rioja`. Bilingual names stay as INE writes them (`Araba/Álava`, `Alicante/Alacant`, `Castellón/Castelló`, `Valencia/València`). Spanish search aliases (Gerona, Orense, Vizcaya…) belong to `constituency-picker`.

**D4. Missing coverage is a problem.** `data check` and `db check` report as a problem (exit 1) any Constituency that no format-2 Party runs in. Every real general election has candidatures in all 52.

**D5. Removed documents are refused.** In a format-2 import, a listed Party whose current bundle row has a `bundle_file` that the manifest no longer lists for that Party is a conflict. Discarding a manifesto is a phase-2 review decision (`ingestion-ledger`), not a removal from the manifest.

## Manifest Format 2

```toml
format = 2
[election]            # unchanged: country, type, date, name
[candidatures]        # required
source = "BOE núm. …, de … de 2026: candidaturas proclamadas …"   # 1..500 chars, trimmed
url = "https://www.boe.es/…"                                     # optional, validate_url
[[parties]]           # 1..N; short_name, name, optional logo (as format 1); no `file`
short_name = "PSC"
name = "Partit dels Socialistes de Catalunya"
constituencies = ["08", "17", "25", "43"]                          # or "all"
[[documents]]         # 0..N (phase 1 may have none)
file = "psc.md"
parties = ["PSC"]
constituencies = ["08"]                                            # optional
```

`read_bundle` accepts format 1 (unchanged) or format 2. Anything else gives `format must be 1 or 2`. Format-2 rules (each failure is a `BundleError` `<file>:<line>: <problem>`):
- Keys: top level is exactly `format`, `election`, `candidatures`, `parties`, plus an optional `documents`. Unknown keys are refused at every level. A format-1 key in format 2 (`file` on a Party) and a format-2 key in format 1 (`constituencies`) are unknown keys.
- A Party's `constituencies` is required, and is `"all"` or a non-empty list of strings. Each string is one of the 52 codes, with no duplicates. TOML integers are refused (`28` → `must be a string such as "28"`). An unknown code gives `unknown Constituency '53' (expected an INE code 01..52; see "ideology constituency list")`. An empty list gives `party PSC has no Constituencies`.
- A document's `file` follows the format-1 pattern and appears in only one document. `parties` is a non-empty list of declared short names with no duplicates. The optional `constituencies` uses the same rules as a Party's, each code must be run by at least one listed Party, and every listed Party must keep at least one code after the intersection. The `.md` front-matter `party` must be one of the document's `parties`. Two documents that list the same Party must not have the same `content_hash`.
- The rules on the directory, slug, PDFs, unlisted top-level `.md` files and `logos/` stay as in format 1. A document file counts as listed.
- `_ManifestLines` must count array-table indexes per section, because `[[documents]]` comes after `[[parties]]`. Today one counter is shared.

## Acceptance Scenarios

1. **Seed.** Given a fresh database, when `ideology db upgrade` runs, then the head is `0016` and `constituencies` holds the 52 rows above. `ideology constituency list` prints `code<TAB>name` for all 52, without needing a database.
2. **Committed DB.** Given a copy of `data/ideology.db` at `0015`, when it is upgraded, then `ideology db check` prints `Safe to commit: yes`, `candidatures` and `source_document_constituencies` are empty, and every row of the existing tables (the old columns of `elections`) is unchanged. The committed file is then upgraded the same way and committed.
3. **Format 1 unchanged.** Given the committed 2023 and 2026 bundles, when they are read, imported into a fresh DB and checked, then the output, ids and problems are the same as before. The existing tests pass, and only the attribute paths change where the bundle types changed.
4. **Format 2 import.** Given a format-2 bundle with a national Party (`"all"`), a regional Party, a shared document and a Party with no document, when it is imported into a fresh DB, then the Parties, candidatures, `elections.candidatures_source(_url)`, one Source Document row per Party × document and their scopes (D1) are created. A second import reports everything unchanged, and `data check` prints `Database matches bundle <slug>: P parties, C candidatures, D documents`.
5. **Changes.** Given an imported format-2 bundle, when a Party gains or loses a Constituency, a document's scope changes, a `.md` changes, or a Party is removed from the manifest, then the import makes the candidatures and the current row's scope equal to the manifest and reports `+`/`-`. A changed file gets a replacement row with the new scope, and the old row keeps its old scope. A Party removed from the manifest loses its candidatures, and its row and documents are left alone. No run is queued for a candidature or scope change alone. In `live`, added or replaced documents queue a run, as today.
6. **Legacy → v2 on one Election (D2).** Given a DB holding the format-1 2026-like Election with a published Dataset Version, when a format-2 manifest for the same Election imports Parties with equal short name and name, plus new candidatures, then the reused rows keep every column (logo too, when the same file is declared). The existing document rows (`pp.md`) stay current and gain scope rows. New Parties get new ids, and `GET /api/v1/dataset-versions/{id}` returns byte-identical JSON before and after.
7. **Refusals before any write.** A conflicting name or short name, a current non-bundle row, a current bundle row no longer listed for its Party (D5), a reverted file, or a bad `url`: the import refuses with `BundleConflictError` / `InvalidInputError`, and the DB is unchanged.
8. **Checks report Constituency problems.** Unknown codes, an empty list and a missing `constituencies` fail `read_bundle`, so `data import` and `data check` fail with the line. Missing coverage (D4), DB candidatures or scopes that differ from the manifest, extra candidatures on unlisted Parties, and a `constituencies` table that differs from the seed are each one `Error:` line in `data check` (exit 1) and in `db check`.

### Existing Patterns To Follow

- All conflicts are found before the first write. Import functions take a Session and never commit. Problem strings use the form `party S (id P): …`.
- The bundle is authoritative for what it lists (logos today), and Parties it does not list are left alone.
- A migration that adds a column uses `recreate='never'`. Each migration gets upgrade, downgrade and offline-PostgreSQL render tests.
- A PR that adds a migration upgrades and commits `data/ideology.db` (`test_committed_database.py`).

## Technical Approach

**Migration `0016_constituencies_candidatures`** (hand-written):
- `constituencies(code String(2) PK, name String(100) NOT NULL UNIQUE)`, then `op.bulk_insert` of the literal 52 rows.
- `candidatures(party_id FK parties.id ON DELETE CASCADE, constituency_code FK constituencies.code, PK(party_id, constituency_code))` with an index on `constituency_code`.
- `source_document_constituencies(source_document_id FK source_documents.id ON DELETE CASCADE, constituency_code FK, PK both)`.
- `elections` gets `candidatures_source String(500)` and `candidatures_source_url String(2048)`, both nullable, added with `recreate='never'`.
- Downgrade reverses all of this. Legacy rows keep NULLs and have no candidature or scope rows.

**Models:** `Constituency`, `Candidature`, `SourceDocumentConstituency`, the two `Election` columns, `Party.candidatures` and `SourceDocument.scope` relationships (passive deletes).

**`ideology_app.constituencies`** (pure, standard library only): `INE_SOURCE_URL`, `CONSTITUENCIES: tuple[tuple[str, str], ...]`, `CODES: frozenset`, `name_of(code)`. `source_bundle` imports it. Database helpers go in `elections`: `constituency_seed_problems(session) -> list[str]`, which is empty when the table equals the tuple.

**`source_bundle`:**
- `MANIFEST_FORMATS = (1, 2)`.
- `Bundle` gains `format: int`, `candidatures: CandidatureSource | None` (source, url) and `documents: tuple[BundleDocument, ...]`.
- `BundleDocument(file, text, parties: tuple[str, ...], constituencies: tuple[str, ...] | None)`. Format 1 derives one document per Party, with `parties=(short_name,)` and `constituencies=None`.
- `BundleParty` gains `constituencies: tuple[str, ...] | None`, sorted and expanded from `"all"`. Its `file`/`text` become optional: they are set only in format 1 (legacy convenience), and new code reads `documents`.
- Add `document_scope(bundle, document, short_name) -> tuple[str, ...]` (the D1 rule).

**`bundle_import`:**
- `import_bundle` and `check_against_bundle` dispatch on `bundle.format`. The format-1 functions stay as they are.
- Format-2 plan, which writes nothing:
  - the Election name conflict;
  - Party matching (D2), with the existing conflict messages;
  - per listed existing Party: a current non-bundle row is a conflict, a current bundle row whose file is not among that Party's documents is a conflict (D5), more than one current row per (Party, file) is a conflict, and a reverted file is a conflict;
  - `validate_url` on `candidatures.url`.
- Format-2 writes:
  - create the Election or Parties when missing;
  - set the candidature source and logos;
  - set the candidatures to the manifest set;
  - delete the candidatures of Election Parties the manifest does not list;
  - per (Party, document): unchanged, added or replaced, keyed by `(party_id, bundle_file)`;
  - set the current row's scope to `document_scope(...)`.
- `ImportReport` gains `format`, `candidature_source_change`, per-Party candidature diffs (added and removed codes), per-row scope diffs and the removed candidatures of unlisted Parties. `new_documents` feeds the live trigger, as today.
- Format-2 check lists:
  - a missing Election or Party;
  - a name, logo, source or url that differs;
  - candidatures that differ (`party PSC (id 30): candidatures differ: missing 25, 43; extra none`);
  - unlisted Parties that have candidatures;
  - the per-document problems of `_document_problems`, plus a scope that differs;
  - unlisted current bundle rows and non-bundle current rows;
  - coverage (`Constituency 51 (Ceuta) has no candidature in election.toml`).

**CLI:**
- `data import` prints format-1 output byte for byte as today. For format 2 it prints per-Party lines (`Party PSC (id 30): created, 4 Constituencies (+4 -0)`), per-row lines (`Document psoe.md for PSC: added source document 41 (272 pages), scope 4`, or `unchanged (…), scope +1 -0`), a source line, and a summary.
- `data check` adds `elections.constituency_seed_problems`.
- `db check` adds the same seed problems for every database. Format-2 bundle checks come in through `check_against_bundle`.
- New group `ideology constituency list` (no database needed).

**Seam for `ingestion-ledger`:** phase 1 is done for a Party when it is listed in a format-2 manifest with Constituencies. The ledger file may live in the bundle directory, because `read_bundle` ignores any file other than top-level `.md`, PDFs and `logos/`. Expose `bundle_import.candidatures_by_party(session, election_id) -> dict[int, tuple[str, ...]]` and `document_scopes(session, election_id) -> dict[int, tuple[str, ...]]`. These are read-only, and later features use them instead of querying the tables directly.
