# Domain Model

> **Model generation.** *Legacy* rules describe Dataset Versions 1–5 (Election 1 = 2023: versions 1–3; Election 2 = 2026: versions 4–5) and the current national pipeline until `statements-from-proposals` and `constituency-selection-validation` replace it. **v2** rules describe the Dataset Versions that pipeline produces; the first real one comes from `e2e-2026-constituencies`. Older versions stay readable and are never rewritten. A Pipeline Run and its Dataset Version carry `model_generation` (`legacy` or `v2`; migration `0018`), set when the run is queued, copied into the Dataset Version at insert and never updated; Dataset Versions 1–5 read `legacy` (`statements-from-proposals`, S7). The `CONSTRAINTS.md` rules that describe the legacy pipeline are not changed here: each is changed by the feature that changes its code (user decision 2026-11-24; owners listed in `docs/risks-and-open-questions.md`, "Constituency redesign").

## Core Concepts

- **Country** — e.g. Spain. Container for Elections.
- **Election** — country, type (`general` for the MVP), date, name.
- **Constituency** (v2, `constituencies-and-candidatures`) — one of the 52 Congreso circunscripciones (50 provinces, Ceuta, Melilla); reference data with an INE code (`01`..`52`) and a Spanish name (INE name, inverted article moved to the front). Seeded by migration `0016`, changed only by migration. Congreso only, no Senado.
- **Party** — name, short name, logo (optional). Linked to an Election (inclusion is per Election; the same real party can appear in several). **v2:** a candidature with its own name and logo that runs in a list of Constituencies (a regional coalition is its own Party); included when it has a manifesto of enough content, otherwise an Excluded Party. *Legacy (Dataset Versions 1–5):* a national ballot ticket (single party or coalition) in a national Party set chosen per Election by user decision (see `docs/risks-and-open-questions.md`): for 2023 (Dataset Versions 1–3), the tickets with seats from the 2023 result, with CCa and UPN not included; for 2026 (Dataset Versions 4–5), the tickets with a seat in the 40dB/EL PAÍS projection of 19 Nov 2026 and an official manifesto, plus Podemos and SALF, with CC and EAJ-PNV not included.
- **Candidature** (v2, `constituencies-and-candidatures`) — Election × Party × Constituency: the Party runs in that Constituency. Entered by the Operator from the proclaimed candidatures (BOE), with the source recorded; never generated by AI. Declared in a format-2 `election.toml` and written only by `ideology data import` (table `candidatures`; the source on the Election). Candidatures with different names that share a manifesto are separate Parties sharing the document (D1, see Source Document). A **legacy-only Party** is a Party row of the Election that the format-2 manifest does not list: it has no candidatures and v2 features ignore it; a format-2 import reuses an existing row only when short name and name are both equal and never renames or deletes one (D2, default for team review).
- **Source Document** — belongs to a Party in an Election; origin `upload` or `url`; stored text plus page mapping for locators, and a content hash for change detection. **v2 scope:** it declares the Parties and Constituencies it applies to. A Source Document listed for several Parties (e.g. a national manifesto shared by the national Party and its provincial coalition) is stored as one Source Document row per Party, sharing the file and its content hash; each row's scope is the Constituencies the document declares, or every Constituency of that Party, intersected with that Party's Constituencies (D1, `constituencies-and-candidatures`; default for team review). A replaced row keeps its old scope; at phase 2 the Operator reviews it and may discard it with a reason. A coalition's joint manifesto takes precedence over a member's (Conflict). *Legacy (Dataset Versions 1–5):* a coalition's joint manifesto is its main Source Document (the first registered version of it, which stays main when a re-fetch replaces it); member parties' manifestos may be attached as extra ones.
- **Proposal** (v2, `proposal-extraction`) — a verbatim concrete measure or commitment from a Source Document (a point or paragraph; diagnosis or context only when relevant), with its page, one or more main categories from the topic catalog (`topic-catalog`, usually one) and free secondary tags. Kept only if its text is on the cited page (Evidence's normalised match). Extracted once per document, reused while the document is unchanged, extracted incrementally over several runs. Never edited. Identified by the document's `content_hash` (one extraction per content, reused across the rows of a shared file and across Elections); each dropped item is recorded with its reason (`not_found`, `other_page`, `context_page`, `duplicate`, `no_letters`).
- **Ingestion Ledger** (v2, `ingestion-ledger`) — the committed per-Election file next to the Source Text Bundle: per Party, the phase reached or the exclusion reason, plus the Operator's conflict decisions. Read by the guided procedure `ingestion-guide`.
- **Conflict** (v2, `proposal-conflicts`) — a flagged contradiction between Proposals of two documents applying to the same Party and Constituency. Two kept documents of a Party whose scopes intersect form an *overlap* (an Ingestion Ledger entry with its Constituencies); an LLM check per shared category records the contradicting Proposal pairs. A coalition's joint manifesto (`joint_for` on its `[[documents]]` entry) precedes a member's automatically; otherwise the Operator decides which document prevails, with a reason, recorded in the Ingestion Ledger. The decision sets aside only the losing document's contradicting Proposals, for that Party and in the overlap Constituencies (C2).
- **Excluded Party** (v2) — a Party with no manifesto, whose manifesto the Operator discarded at review, or with fewer than N validated Proposals (configurable, default 30). N counts per Party, summing all its Source Documents; the Party is Excluded only if the total is below N (user decision 2026-11-24; `proposal-extraction`, `ingestion-ledger`). Recorded with its reason; shown only in the results note of each Constituency where it runs, never ranked or scored.
- **Statement Rewording** (v2, `statement-rewording`) — an Operator's rewording of a confusing Statement without changing its meaning, given as an input file of a new run: AI text, new text and reason are stored; Party Positions and Evidence are unchanged. An LLM equivalence check rejects a change of meaning; a rejected rewording does not fail the run: the Statement keeps its AI text and the pipeline report shows the rejection (user decision 2026-11-24).
- **Pipeline Run** — belongs to an Election; records the LLM provider, model, prompt versions, Generation Mode, timestamps, LLM usage (calls and tokens), status, the Validation thresholds it was validated with, and Validation report. Every successful LLM call is recorded as it returns (task, request fingerprint, validated output, tokens); a run started with `--resume-from` (an unfinished run) or `--reuse-from` (any earlier run, even one with a Dataset Version) names the earlier run whose identical calls it reuses (`pipeline-run-checkpoint`, `pipeline-coverage-selection`). *Legacy (Dataset Versions 1–5 and the current pipeline; for v2 see CONTEXT.md, Pipeline Run):* it also records its Statement Selection: the Statement Pool with each Statement's scores, which Statements were kept and why (`pipeline-coverage-selection`), and the findings discarded during extraction because their quote was not on the cited page, with the stances they cleared (`pipeline-verified-findings`). It records its anchor Dataset Version: the Published Dataset Version whose Statements were given to Statement generation as Anchors (prompt input only), or none; a run started with `--resume-from` / `--reuse-from` inherits the anchor version of the run it names when that run recorded one, and the Statement Selection notes which Anchors reached the pool and the Questionnaire (`pipeline-statement-clarity-context`). `ideology pipeline report` shows all of it, read-only.
- **Dataset Version** — produced by one successful Pipeline Run; contains the Statements and the Party Positions. Immutable. **v2:** per Constituency, its availability (available, or unavailable with a reason), its ordered Statements (the Questionnaire), its offered lengths (20/30/40/50 when that many valid Statements exist; `Todas (N)` only when fewer than 20, user decision 2026-11-24) and its Excluded Parties with their reasons (`constituency-selection-validation`); and each non-Excluded Party's counted Proposals in counted order with the Constituencies where each counts (table `dataset_version_proposals`, `public-dataset-api-v2`), from which the Comparador reads a Party's Proposals per Constituency and category. *Legacy (Dataset Versions 1–5):* one national Questionnaire (in priority order since `pipeline-statement-priority-tiers`) and its Questionnaire Lengths (e.g. 15, 30 and the full count; a questionnaire of length N is the first N Statements; NULL, read as the full length only, on versions created before it existed).
- **Statement** — text, order and Context Note (a neutral AI-generated explanation of what it names; null on Dataset Versions created before `pipeline-statement-clarity-context`, never backfilled); belongs to a Dataset Version. **v2:** its source Proposals (the group it was built from, in citation order; table `statement_proposals`), one category from the topic catalog (stored as its topic), and the Constituencies where it is valid (`constituency-selection-validation`). Source Proposals may go in either direction (`statements-from-proposals`, S1, S12). *Legacy (Dataset Versions 1–5):* a topic tag, generated from the Party-balanced Agenda.
- **Party Position** — (Dataset Version, Statement, Party) → value in {−2..+2, no stance} + Evidence. **v2:** a Party may be against a Statement only when one of its Proposals backs that; no related Proposal = no stance. Still one Position per (Dataset Version, Statement, Party); it applies in a Constituency only when one of its Evidence Proposals counts there for that Party, otherwise it reads as `no stance` there (S5; applied by `constituency-selection-validation`).
- **Evidence** — **v2:** one or more Proposals of the positioned Party (verbatim text, page, Source Document locator), ranked in citation order (table `party_position_proposals`), each with the Constituencies where it counts for that Party, frozen in the Dataset Version. Rank 1 is mirrored into the Position's quote columns (the Proposal text exactly, its page, its Source Document and URL) (S6). *Legacy (Dataset Versions 1–5):* quote, Source Document reference, page and/or URL anchor.

## Relationships

- Country 1—N Election 1—N Party
- Election 1—N Party N—M Constituency (candidatures; v2)
- Party 1—N Source Document (per Election)
- Source Document N—M Constituency (scope; v2)
- Source Document 1—N Proposal (v2)
- Proposal N—M main category of the topic catalog, plus free tags (v2)
- Election 1—1 Ingestion Ledger (v2)
- Election 1—N Pipeline Run 1—0..1 Dataset Version
- Dataset Version 1—N Statement; Dataset Version × Statement × Party → 1 Party Position
- Statement N—M Proposal (its source group; v2)
- Party Position → 1..N Proposals of the same Party as Evidence (v2), or 0..1 quote Evidence (*Legacy*); required unless `no stance`
- Dataset Version × Constituency → availability (or reason), ordered Statements, offered lengths, Excluded Parties with reasons (v2)
- Dataset Version × Party → 0..N counted Proposals, each with the Constituencies where it counts (v2, non-Excluded Parties only)
- Election → 0..1 Published Dataset Version

## States and Lifecycles

**Election**: `draft` → `active` (has a Published Dataset Version; set by its first publish, in the same transaction) → `archived` (after the election day; still viewable, labelled as historical).

**Source Document**: `registered` → `fetched` (URL downloaded or upload stored) → `parsed` (text extracted) | `failed`. A `parsed` URL document can also be marked **replaced** (`replaced_by_id`, not a status) when a re-fetch found new bytes: a new `parsed` row for the same Party and URL takes its place, and the old row keeps its hash, pages and file for the Evidence of older Dataset Versions. Pipeline Runs read only current (not replaced) documents. A document imported from a Source Text Bundle (`ideology data import`) has `bundle_file` set (the `.md` name): it is created directly `parsed` with no stored file, its `content_hash` is the SHA-256 of the `.md` file, its origin is `url` when the file has a `source_url` (Evidence links to it) and `upload` otherwise, it is replaced only by a re-import of a changed file (same replacement rule as a re-fetch), and it is never re-fetched.

**Pipeline Run**: `queued` → `running` → `validating` → `passed` | `failed`.
- `passed` → its Dataset Version is published automatically, in the same transaction as its Validation results, and replaces the previous one, unless the Published version belongs to a newer run (higher Pipeline Run id): then it stays `candidate` and the newer version stays live. Publish order is queue order, so an older run never rolls Voters back to staler data.
- `failed` → nothing is published and the previous Published version stays live; the Validation report says why. The Operator can re-run.
- A run that fails Validation keeps its `candidate` Dataset Version, which is never published.

**Run triggers**: in `precomputed` mode, the Operator. In `live` mode, a Pipeline Run is queued automatically when a Source Document is added (ending `parsed`) or its content hash changes, in the same transaction as the document, and executed by the Operator's queue command (`ideology pipeline run-queued`). A `data import` that adds or replaces a bundle document counts as "added / content changes" (one run per import at most, in the import transaction). At most one run per Election is `queued`: later changes join it, since it reads every parsed document when it starts. A run already `running` or `validating` does not absorb a change; a new run is queued. Same bytes for the same Party are a duplicate, so nothing is queued. URL sources are re-fetched by the Operator's `ideology source refetch` (to be scheduled, e.g. by cron) once their last check is at least `SOURCE_REFETCH_INTERVAL_HOURS` old (default 6), in both modes: new bytes register a replacement document, and in `live` that queues (or joins) a run in the same transaction; the same bytes only record the check time; bytes another document of the same Party already has are reported as a duplicate and change nothing; a failed download keeps the old document and queues nothing.

**Dataset Version**: `candidate` → `published` → `superseded`. Superseded versions stay readable so old Share Links keep working. The status is the only thing that ever changes; a superseded version is never published again.

**Ingestion phases** (v2, `ingestion-ledger`, guided by `ingestion-guide`): 1 candidatures per Constituency → 2 provide and review manifestos → 3 extract Proposals → 4 generate Statements (the Pipeline Run). Per Party, the Ingestion Ledger moves from candidature declared → manifesto provided and reviewed → Proposals extracted; a Party may instead become Excluded, with its reason, at any of those steps (no manifesto, manifesto discarded at review, or fewer than N validated Proposals summed over all its Source Documents after phase 3). The values written in the file: `phase` ∈ `candidature_declared`, `manifesto_reviewed`, `proposals_extracted`, `excluded`; `reason` ∈ `no_manifesto` (an explicit Operator decision for a Party listing no document), `discarded_at_review`, `too_few_proposals`. Review is per document (`kept`, or `discarded` with `no_text_layer`, `not_a_manifesto` or `incomplete`) and applies to every Party listing it; a changed file voids its review and count. A Party is Excluded `discarded_at_review` only when every document it lists is discarded; a partly discarded Party goes on with its kept documents, and only they count toward N (L4, default for team review). Phases are derived from these facts, never set directly.

**Conflict** (v2, `proposal-conflicts`): overlap `unchecked` → `no_contradiction` | flagged → `joint_manifesto` (exactly one document is the Party's joint manifesto; automatic) | `pending` → `decided` (the Operator names the prevailing document, with a reason; re-deciding overwrites). The status is derived, never set. Checks and decisions are recorded in the Ingestion Ledger (ledger format 2) and applied by the run through `counted_proposals`; only the losing document's contradicting Proposals are set aside, per Party and Constituency; Proposals are never edited. A content change of either document clears the check and the decision; a scope change keeps both.

**Phase 4 gate** (v2): a phase 4 run (`ideology pipeline run-v2 DIR`) is refused while any Party is neither Extracted nor Excluded, any overlap of a non-Excluded Party is unchecked or pending (C9), the Ingestion Ledger is out of date, the Election is not imported, or a ledger Proposal count differs from the database; a refusal creates no run (`statements-from-proposals`). A passed v2 run is published like a legacy one, superseding the Election's Published version of either generation (`constituency-selection-validation`, K12). In `live` mode an Election with candidatures never gets a queued run; its phase 4 is started by the Operator (S11). The legacy run is refused on an Election with candidatures (S10). A v2 run uses no Anchors (S8).

**Constituency availability** (v2): fixed when the Dataset Version is created (available, or unavailable with its reason) and immutable with it.

A Statement Rewording adds no state: it only feeds a new run, and an applied one is stored with the new Dataset Version (`statement_rewordings`).

## Validation Checks (initial set)

### Legacy (Dataset Versions 1–5 and the current pipeline)

1. Every Statement is unique (same text after normalisation: case, accents, whitespace and punctuation ignored); otherwise the whole run fails. Single-proposition detection (no "and/or" compounds) is not automated yet; only the prompts require it.
2. Every non-`no stance` Position has Evidence whose quote, normalised, starts on the cited page (or runs onto the next) of a Source Document the run read for that Party. Normalisation folds case, accents and ligatures and drops whitespace and punctuation; otherwise the match is exact.
3. Each Party is in favour (+1/+2) or against (−1/−2) on at least the configured share of Statements (default 50%; 0 and `no stance` do not count), on every offered Questionnaire Length (each prefix: the first 15, the first 30 and the full set by default); otherwise the whole run fails.
4. Each Statement separates the parties: at least one Party in favour (+1/+2) and one against (−1/−2), with 0 and `no stance` counting on neither side (an Election with fewer than two Parties fails); otherwise the whole run fails.
5. The Statement count is within the configured range (default 35–40), and the stored Questionnaire Lengths are the configured shorter lengths (default 15, 30) below the count, then the count; otherwise the whole run fails.
6. Topics are spread out: no single topic accounts for more than a configured share of the Statements (default 30%; a topic fails when strictly above it), on every offered Questionnaire Length; otherwise the whole run fails.
7. Every Statement has a Context Note whose trimmed length is within the configured range (default 30–300 characters) and that uses no word of a configured list of evaluative words (whole words, case and accents ignored); otherwise the whole run fails. Statement Selection leaves out pool Statements whose note would fail, so in practice a bad note costs one Statement. A note's factual accuracy is not checked (`pipeline-statement-clarity-context`).

### v2

- **Unchanged:** 1 (uniqueness); 2 (Evidence on the cited page, now applied to the Evidence Proposals, which must belong to the positioned Party); 7 (Context Note). Since `statements-from-proposals` a v2 run is checked with `evidence_quotes` (on the mirrored rank-1 Evidence), `evidence_proposals` (a sided Position has 1 or more Evidence Proposals, ranked 1..n, and a `no stance` one has none; each Evidence Proposal comes from a run document of that Party, has that document's content hash, starts on its page, and lists at least one Constituency; rank 1 equals the mirrored columns), `statement_sources` (every Statement has 1 or more source Proposals, each from a run document), `statement_uniqueness` and `context_note`. Before positioning, a deterministic party-blind filter leaves out pool Statements whose note would fail check 7 and exact duplicates, so checks 1 and 7 pass by construction.
- **Per Constituency** (`constituency-selection-validation`, defaults for team review in `docs/risks-and-open-questions.md`): 3 (coverage: every Party running there takes a side on at least 5 valid Statements), 4 (separation among the Parties running there: validity) and 5 (a minimum of 10 valid Statements; offered lengths 20/30/40/50/`Todas (N)`) are applied by Constituency Selection before the Dataset Version is written; a Constituency failing them is stored unavailable with its reason (`low_party_coverage`, `too_few_statements`, or `fewer_than_two_parties`) and the run does not fail. 6 (topic spread) only shapes each Constituency's order (K6). Validation then runs `constituency_snapshot`, `constituency_validity`, `constituency_availability` and `constituency_order`, which recompute the stored rows and fail the run only when they were written inconsistently, or when no Constituency is available (K8). Rules: K1 a Statement is valid in a Constituency when, among the non-Excluded Parties running there (from the Dataset Version's frozen candidature copy) and reading a Position there only when one of its Evidence Proposals counts there (S5), at least one is in favour and one against; K2 the valid Statements are ordered by (Parties with a side there, the smaller side, pool order), then a topic is deferred past each offered length shorter than the set once it holds 30 % of that length (`VALIDATION_MAX_TOPIC_SHARE_PERCENT`), and every valid Statement is placed; K3 a Constituency needs at least 10 valid Statements (`VALIDATION_V2_MIN_STATEMENTS`); K4 every Party running there needs a side on at least 5 of them (`VALIDATION_V2_MIN_PARTY_SIDES`); K5 otherwise it is unavailable with the first failing reason: `fewer_than_two_parties`, `too_few_statements`, `low_party_coverage`; K6 topic spread only shapes the order and is never a reason or a failure; K7 a Statement valid in no available Constituency stays in the Dataset Version but in no Questionnaire; K8 the run fails only when no Constituency is available.
- **New gates outside the numbered checks:** a Proposal is kept only when its text is verbatim on its page (`proposal-extraction`); the Excluded threshold, N validated Proposals per Party summed over its Source Documents (`proposal-extraction`); the phase 4 gate (`ingestion-ledger`, `proposal-conflicts`); the rewording equivalence check (`statement-rewording`: it runs after Party Positions are assigned and before Constituency Selection, one `statement_rewording_check` LLM call per rewording that matches a kept Statement and does not duplicate another Statement's text; each entry ends `applied`, `rejected`, `duplicate` or `not_found`, and none of them fails the run: a rejected Statement keeps its AI text and the pipeline report shows the rejected rewording, user decision 2026-11-24). The check `statement_rewording` (appended to the v2 checks) then confirms that every stored rewording has an `applied` verdict in the run's report and vice versa.

## Important Scenarios

- An Operator adds a URL manifesto; it is fetched, parsed, and included in the next run.
- A run fails check 2 for one party; nothing is published; the Operator re-runs it.
- A Voter marks 5 Statements Important and answers Neutral on 3 of them; those 3 marks are dropped, and the scores reflect the 2 remaining weights and the exclusions. In v2 there is no cap on Important marks (`important-unlimited`).
- A Voter opens a layout `v1` or layout `v2` Share Link (layout `v1` predates the three-option scale; layout `v2` is the format of every link made since `three-option-scale`; both layouts point only to Dataset Versions 1–5); they see the outdated-version notice with a `Haz el nuevo cuestionario` link, never a result or a broken page (`share-link-v3`).
- A Voter opens a current-layout Share Link from a superseded Dataset Version; they see that version's result and a notice that newer data exists.
- A Voter in Granada is scored only against the Parties running in Granada; ERC, which does not run there, is not shown.
- An Operator follows phases 1–4 with `ingestion-guide`; the phase 4 run is refused while one Party is still pending (neither Extracted nor Excluded).
- A Voter answers 20 Statements, then `Contestar 5 más`, then `Ver resultado`; the Share Link reopens that result over the 25 answered Statements.
- *Legacy (Dataset Versions 1–5):* a run's full set of 40 Statements meets coverage, but one Party takes a side only on Statements ranked 16 and below, so the first 15 fail check 3: the whole run fails, nothing is published and no length is dropped; the Operator tunes the settings (lengths, threshold) and replays with `--reuse-from` (`pipeline-statement-priority-tiers`).

## Edge Cases

- A coalition whose joint manifesto contradicts a member party's own manifesto: the joint manifesto takes precedence automatically. Other contradictions between documents applying to the same Party and Constituency are flagged Conflicts decided by the Operator with a reason (`proposal-conflicts`). *Legacy (Dataset Versions 1–5):* precedence was a prompt rule.
- A party that split from a ticket after the election (e.g. Podemos from Sumar) is not a separate Party for that Election.
- A manifesto available only as a scanned PDF (no text layer).
- *Legacy (Dataset Versions 1–5):* a party with no manifesto for the Election → 0% coverage → Validation fails the run (the pipeline never excluded a Party; the Operator did not include some Parties in an Election, by user decision). In a two-Party Election no Statement then separates the Parties either, so check 4 also names every Statement.
- **Excluded Party** (v2): a Party with no manifesto, a discarded one, or fewer than N validated Proposals summed over its Source Documents is listed with its reason in the results note of every Constituency where it runs, never ranked. A Constituency whose remaining Parties cannot separate falls under the unavailable rule.
- **Unavailable Constituency** (v2): published unavailable with its reason, disabled in the list and the map. The rest of the Dataset Version publishes. Expected never to happen in practice.
- **Flagged conflict** (v2): phase 4 waits for the decision. The decision and its reason are recorded in the Ingestion Ledger and applied by the run: the losing document's contradicting Proposals do not count for that Party in the overlap Constituencies. Proposals are not edited.
- **Both or neither joint** (v2): when both documents of an overlap, or neither, are marked joint for the Party, a flagged conflict goes to the Operator (C3).
- **Reworded Statement** (v2): the new Dataset Version holds the final text. The AI text and the reason are stored. Party Positions and Evidence are identical. The previous version and its Share Links are untouched. A meaning change is rejected by the equivalence check; the Statement then keeps its AI text, the run does not fail, and the pipeline report shows the rejected rewording.
- Ceuta and Melilla (v2), with few candidatures: per-Constituency validity applies as anywhere else (minimums 10 valid Statements and 5 sides per Party, `constituency-selection-validation` K3–K4); if their Parties cannot meet the minimums, the Constituency is unavailable with its reason and the run still publishes.
- A v2 Statement valid in no available Constituency stays in the Dataset Version with its Positions and Evidence, but in no Questionnaire (K7).
- A Party running in a single Constituency (v2): scored only there, and counted only in that Constituency's per-Constituency checks.
- Candidatures sharing a manifesto under different names (v2): separate Parties; the document is listed once with every Party it applies to and stored as one row per Party, each with its own scope (D1, `constituencies-and-candidatures`). Example: Navarra's `UPN-PP` (only `31`) shares `pp.md` with `PP` (every Constituency) and has its own `upn.md`.
- A Constituency in which no Party runs (v2): `data check` and `db check` report it as a problem (D4); every real general election has candidatures in all 52.
- The user answers Neutral on every Statement → no ranking; prompt them to repeat the questionnaire and answer at least one with a side.
- In `live` mode a source change can supersede the Questionnaire a Voter is in the middle of; their session keeps the Dataset Version it started with.
