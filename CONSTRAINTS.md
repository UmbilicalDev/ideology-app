# Constraints

Durable MUST / MUST NOT rules. Each has a short reason. Add a rule only when it is real and not already covered by `AGENTS.md` or `ARCHITECTURE.md`.

## Data And Migrations

- The schema MUST change only through Alembic revisions in `src/ideology_app/migrations/versions/`. Never call `Base.metadata.create_all` outside throwaway experiments. Reason: one migration history for SQLite (dev) and PostgreSQL (target).
- The separate feedback store has its own Alembic environment: its schema MUST change only through revisions in `src/ideology_app/feedback/migrations/versions/`, applied only by `feedback.store.upgrade_schema` (app startup and `ideology feedback upgrade`) and versioned in `feedback_alembic_version`. Feedback tables MUST NOT join `models.Base.metadata` or the shared-DB migrations. Reason: the shared-DB head stays single (`db.head_revision()` assumes one head), the feedback store never travels with the committed database, and an existing `feedback.db` must keep its messages on every upgrade (`feedback-api`, `feedback-admin`).
- Autogenerated revisions MUST be reviewed by hand before they are kept. Reason: autogenerate emits each non-native Enum CHECK three times (the Enum's own plus two explicit `sa.CheckConstraint`s), which gives duplicate constraint names on PostgreSQL; delete the explicit `sa.CheckConstraint` lines and confirm `alembic check` reports no drift.
- DDL and queries MUST stay portable to PostgreSQL: no SQLite-only types, functions or SQL. Enums MUST be non-native (`native_enum=False, create_constraint=True`) with exactly one CHECK each. Reason: SQLite is only the dev default.
- Every Engine that is created MUST be disposed (`finally: engine.dispose()` or `ctx.call_on_close`). Reason: on Python 3.15 an undisposed SQLite engine emits `ResourceWarning: unclosed database`, which fails the pytest gate (`filterwarnings = ["error"]`).
- A migration MUST NOT recreate (batch copy-and-move) a SQLite table that other tables reference with `ON DELETE CASCADE`: migrations run with `PRAGMA foreign_keys=ON`, so dropping the old table deletes every child row. Use plain `ADD COLUMN` / `DROP COLUMN` (`op.batch_alter_table(..., recreate='never')`; SQLite ≥ 3.35) as `0008` does, and test the downgrade with child rows. Since `0018` this includes `party_positions` (referenced by `party_position_proposals` with `ON DELETE CASCADE`) and `statements` (by `statement_proposals`). An Enum column added this way MUST spell its CHECK as a named column-level `sa.CheckConstraint` on a `String`, as `0018` does: on SQLite, Alembic skips an Enum's implicit CHECK on `ADD COLUMN` (with a warning), which would leave the column unchecked. Reason: a downgrade of `pipeline_runs` that recreated the table deleted every Dataset Version in testing; `0003`'s downgrade already loses `source_document_pages` this way (see `docs/risks-and-open-questions.md`).
- Tests MUST use a temporary SQLite database (the `db_url` / `migrated_engine` fixtures, or `--database-url` for the CLI) and MUST NOT touch `./ideology.db`. Reason: the default URL is relative to the current directory; `tests/conftest.py` unsets `DATABASE_URL` and changes into `tmp_path` for every test as a safety net.

## Constituencies And Candidatures

- The `constituencies` table MUST change only by migration, and MUST equal `ideology_app.constituencies.CONSTITUENCIES` (`tests/test_constituencies.py`, `data check`, `db check`). Reason: INE codes are reference data every machine and every Dataset Version must agree on; the migration keeps its own literal copy, so only the test keeps the two in step (`constituencies-and-candidatures`).
- Candidatures, document scopes and the Election's candidature source MUST be written only by `ideology data import` of a format-2 `election.toml`, never by AI or by another command, and later features MUST read them only through `bundle_import.candidatures_by_party` and `bundle_import.document_scopes`. Reason: the BOE proclamation, recorded in the committed manifest, is the single source; one read seam keeps later features off the tables. The view-only ORM relationships `Party.candidatures` and `SourceDocument.scope` exist for this feature's import and checks; they are not a read path for later features.
- A Party row referenced by a Dataset Version MUST NOT be renamed or deleted; a format-2 import reuses an existing row only when its short name and name are both equal, and otherwise creates a new row. Reason: `GET` Dataset Version reads Party names and logos live from `parties`, so Dataset Versions 1–5 and their Share Links must keep showing the same Parties (D2).
- Dataset Versions MUST NOT read live candidatures or scopes; the Parties running per Constituency MUST be copied into the Dataset Version when it is created (`dataset_version_candidatures`, written by `_finish_v2`; `constituency-selection-validation`), and `data check` / `db check` MUST NOT compare that copy with live candidatures. Reason: Dataset Versions are immutable, and candidatures change with every format-2 import, which must not invalidate a published version.

## Ingestion Ledger

- `data/elections/<slug>/ingestion-ledger.json` MUST be written only by `ingestion_ledger` functions (through `ideology ingestion` commands, `ideology conflicts decide` (`decide_conflict_in_dir`), `record_extraction_in_dir` and `record_conflict_check_in_dir`), never by hand. LLM output MUST enter it only as a conflict check recorded by `ideology conflicts detect` (`record_conflict_check`), never in any other way (`proposal-conflicts`). Reason: the reader accepts only canonical bytes, and every fact in it is an Operator or phase-3 decision; a git merge conflict on it is resolved by taking one side and rerunning the commands.
- A Party's `phase`, `reason` and `proposals` MUST be derived from the recorded facts and the bundle (`reconcile`), never set directly; phase 3 records only a document's validated Proposal count (`record_extraction`). Reason: one derivation rule (L4 partial discard, L5 per-file review, L7 summed N) on every machine.
- A conflict entry's overlap (files, Constituencies, `joint`) and its `status` MUST be derived (`reconcile`), never set; only the check (`record_conflict_check`) and the Operator decision (`decide_conflict`) are facts, and both are dropped when either document's content hash changes (C5). Reason: the same committed file must give the same gate on every machine (`proposal-conflicts`).
- A v2 Party MUST be Excluded only for one of the three ledger reasons (`no_manifesto`, `discarded_at_review`, `too_few_proposals`). Reason: an Excluded Party changes the Voter's ballot, so exclusion is an explicit, recorded Operator or threshold decision.
- Later features MUST read the ledger only through `party_states` / `require_phase4_ready` (and `pending_conflicts`), except phase 3 (`proposals.store.read_phase3`), which reads `Ledger.documents` through `read_ledger` + `reconcile` and refuses unless the two are byte-identical, and `proposals.conflicts`, which reads `Ledger.conflicts` / `documents` through `read_phase3`; Dataset Versions MUST copy the Excluded Parties and their reasons when they are created (`dataset_version_candidatures.excluded_reason`, from `load_phase4`'s snapshot; the ledger `note` is not copied) and MUST NOT read the ledger live (`constituency-selection-validation`). Reason: Dataset Versions are immutable, and the ledger keeps changing.
- `min_proposals` (N) MUST live in the ledger file, changed only by `ideology ingestion update --min-proposals N`, never in an environment variable. Reason: an environment value could differ between machines, and `data check` would then derive different exclusions from the same committed file.

## Proposals

- Phase 4 MUST read a Party's Proposals only through `proposals.conflicts.counted_proposals` (after `require_phase4_ready`), never through `load_proposals` directly. Reason: it is the one place that sets aside the losing document's contradicting Proposals per Party and Constituency (C2); reading around it would silently ignore Conflict decisions (`proposal-conflicts`).
- A change to the `proposal_conflict_check` system text, template or schema MUST bump `PROPOSAL_CONFLICT_CHECK.version` and the fingerprint pinned in `tests/test_conflict_prompts.py`; its prompt MUST show only Proposal text and the category name, never Party names, file names or pages. Reason: recorded checks name their prompt version, and the comparison must not depend on who the Party is (`proposal-conflicts`).
- Proposal extraction state MUST be per document content (`content_hash`): at most one `proposal_extractions` row per hash, reused by every Source Document row and Election with those bytes, never keyed by Dataset Version or row id. Reason: a shared file (D1) or unchanged bytes must never be paid for twice (`proposal-extraction`, P3).
- `proposal_extraction_calls` and `proposals` rows MUST only be inserted, and a complete extraction MUST NOT be updated, redone or deleted; the single exception is `ideology proposals extract --restart F`, which deletes the calls and row of an `in_progress` extraction. Reason: Dataset Versions will reference Proposal ids, and recorded calls are what a resume replays (P4).
- Proposals MUST be written only by finalize (`proposals.store._finalize`), in one transaction, with text, page, categories and tags exactly as the provider returned them, and only for items that pass the strict check (`find_quote_miss` on the cited page, not the context page, not an exact normalised duplicate); no quote repair. Reason: AI output is never edited, and a Proposal must be verifiable on its page (P1, P5).
- Any change to the `proposal_extraction` system text, template, `max_tokens` or output schema (`proposals/prompts.py`) MUST bump `PROPOSAL_EXTRACTION.version` and its fingerprint in `tests/test_proposal_prompts.py`; it MUST NOT be added to the legacy `PROMPTS` / `PROMPT_VERSIONS`. Reason: an in-progress extraction is pinned to its prompt version, and legacy fingerprints and recorded calls must stay unchanged.
- No Party name, short name or file name MAY reach the `proposal_extraction` prompt; only page text does. Reason: perceived bias, as for the legacy pipeline.
- A resumed extraction MUST use the provider, model, prompt version and chunk size it was created with and reuse a recorded call only for an equal `request_hash` after re-validating its output; anything else is refused until `--restart`. Reason: one document's Proposals must come from one model and prompt (P10).
- Phase 3 MUST write the ledger only through `ingestion_ledger.record_extraction_in_dir` (the validated count of a complete extraction, once per `content_hash`), and MUST NOT set a phase or exclude a Party itself. Reason: `too_few_proposals` follows from the summed counts and N on every machine (exclusion side of the coverage rule).

## Source Documents

- Only `src/ideology_app/pdf_text.py` MAY import `pypdf` in application code. Reason: one adapter to swap or harden the PDF library; tests may use pypdf only to build fixtures (`tests/pdf_factory.py`).
- Stored Source Document files MUST be content-addressed (`<SOURCE_FILES_DIR>/<sha256>.pdf`) and MUST NOT be overwritten, edited or renamed. Reason: the content hash identifies the exact bytes that Evidence quotes come from, and several rows may share one file.
- Page text MUST be stored as extracted (only NUL characters removed). Any whitespace/accent normalisation for quote matching MUST happen at match time. Reason: Evidence must stay verifiable against the original extraction.
- Tests MUST build PDFs with `tests/pdf_factory.py` (no committed binaries, no network) and MUST point `SOURCE_FILES_DIR` / `files_dir` into `tmp_path`, never `./source_files`. Reason: the default directory is relative to the current directory.

- Only `src/ideology_app/http_fetch.py` MAY fetch Source Document URLs (`urllib.request` / `http.client`), and it MUST allow only `http`/`https`, including after redirects (no `file:`, `ftp:` or `data:` handler). Reason: one place to harden downloads, and an Operator-typed URL must not read local files.
- Every caught `urllib.error.HTTPError` MUST be closed. Reason: on Python 3.15 an unclosed `HTTPError` emits `ResourceWarning: Implicitly cleaning up`, even with `fp=None`, which fails the gate; test fakes build it with `io.BytesIO(b"")` (`tests/http_fakes.py`).
- Tests MUST NOT open a network connection: mock `ideology_app.http_fetch._open` (or pass `fetch=` to `add_url_document`) and keep the autouse socket guard in every module that touches URL fetching. Reason: a deterministic, offline CI.
- A URL Source Document whose re-fetched bytes changed MUST become a new row (same Party and URL); the old row MUST only get `replaced_by_id` and `last_checked_at`, and its content hash, pages and stored file MUST NOT change. Reason: Evidence of older Dataset Versions points at the old row (`evidence_source_document_id`, `pipeline_run_source_documents`).
- Pipeline input MUST be only current documents (`replaced_by_id IS NULL`, via `runs._parsed_documents_query`). Reason: one version per URL lineage; a replaced version must never be read again.
- Source Text files (`data/elections/<slug>/*.md`) MUST be written only by `ideology source extract` and MUST NOT be edited by hand; they MUST be read and written as bytes (no text-mode newlines, no `splitlines()`), and only `ideology_app.source_bundle` MAY parse or serialise them. Reason: `text_sha256`, the canonical-form check and the per-Party content hash make any edit a different document, and the text must stay exactly what pypdf extracted.
- No PDF MAY be committed under `data/` (`.gitignore` `data/**/*.pdf`; `read_bundle` refuses a `*.pdf` in a bundle). Reason: repository size; the `.md` files are the source of truth once extracted.
- A bundle Source Document (`bundle_file` set) MUST NOT be re-fetched, and MUST change only through `ideology data import` of a changed file, which inserts a replacement row and sets only the old row's `replaced_by_id` (as for a re-fetch). Reason: the committed file is the single writer of its page text, and old Evidence points at the old row.
- Tests MUST build bundles in `tmp_path` (`tests/bundle_factory.py`); the committed bundles are only read (`tests/test_source_bundle.py`). Reason: tests must never change committed data.
- A re-fetch MUST NOT write a Source Document row, a file or a Pipeline Run when the download, the PDF check or the text extraction fails (pages are extracted before the replacement row is inserted); only `last_checked_at` is recorded. Reason: a failing site must never hide the parsed document or queue a run.

## LLM Providers

- Only `ideology_app.llm.*_provider` modules MAY import a vendor LLM SDK (e.g. `anthropic`); tests of that adapter are the only other exception. Everything else gets a provider through `build_provider` or by injection. Reason: the provider is configuration, not code branches.
- Tests MUST NOT need or read a real API key and MUST NOT open a network connection. Use `FakeProvider`, or inject an SDK client backed by `httpx2.MockTransport`, and keep the autouse env/socket guard in every LLM test module. Reason: the AGENTS.md invariant and a deterministic, offline CI.
- API keys MUST NOT appear in reprs, error messages or logs; error messages from provider failures carry only the exception class name and HTTP status. Reason: keys leak through tracebacks and Pipeline Run records.
- Only `ideology_app.llm.claude_code_provider` MAY spawn the Claude Code CLI (`subprocess`), always through its `run_cli` seam. Tests MUST NOT spawn it: inject `runner` / `which` or patch the seams, and keep the autouse guard that stubs `run_cli` / `find_cli`. Reason: tests never call a real LLM, and the CLI would use the Operator's subscription.
- The `claude_code` child environment MUST strip every `ANTHROPIC_*` and `CLAUDE*` variable except `CLAUDE_CODE_OAUTH_TOKEN` and `CLAUDE_CONFIG_DIR`, the provider MUST NOT read or pass an API key, and `--bare` MUST NOT be used. Reason: an inherited key or session token would bill the API or authenticate as another session (the one real call during planning failed with 401 for exactly this reason); `--bare` forces API-key auth.
- `claude_code` MUST NOT be used in a deployment or to serve Voters; it is for local Operator runs with the Operator's own subscription. Use `anthropic` there. Reason: subscription terms and usage limits, and the in-process multi-hour waits.
- An `AnthropicProvider` that creates its own client MUST be closed (`with provider:` or `close()`). Reason: an unclosed HTTP client can emit a `ResourceWarning`, which fails the gate.
- The `generate_statements` request schema MUST take its Statement Pool bounds from the same `ValidationSettings` object that the run's Validation uses, through `generation.pool_bounds` (never a second copy). Every Statement or candidate number that an LLM output schema accepts MUST be bounded to the numbers listed in that request (`statement_set_schema`, `finding_list_schema`, `position_list_schema` in `pipeline/prompts.py`). Reason: such output then fails at the call that produced it, not hours later at Validation or silently as a stance on a Statement that does not exist (`pipeline-output-bounds`).

## Pipeline

- Any change to a prompt's system text, template or output schema in `src/ideology_app/pipeline/prompts.py` MUST bump that prompt's `version` and its fingerprint in `tests/test_pipeline_prompts.py`. Reason: each Pipeline Run records `prompt_versions`, which must identify the prompt actually used.
- The pipeline MUST NOT send Party names or short names to the LLM in any prompt (Statements or Party Positions; only page text, Statement texts and ids reach `generation.py` and `positions.py`). Reason: perceived bias, and the UI treats all parties identically.
- Dataset Versions, Statements, Party Positions and their Evidence MUST NOT be updated or deleted by application code (only database cascades delete them). The one exception is a Dataset Version's `status` (see the publishing rules below). Statements are stored exactly as the provider returned them, except a v2 Statement whose Statement Rewording passed `statement_rewording_check` in that run: `statements.text` is the Operator's text and `statement_rewordings.ai_text` holds the provider's text exactly (`statement-rewording`); rejecting bad Statements is Validation's job. Reason: Dataset Versions are immutable and AI output is never edited (a Statement's text changes only through a recorded Statement Rewording in a new run).
- Evidence quotes MUST be stored exactly as the LLM returned them (pages too). Any normalisation MUST happen only when matching (`validation-evidence-quotes`) or for display. Reason: Validation and Voters must see what the model actually cited.
- A Dataset Version MUST be written only together with all its Statements and Party Positions, in one transaction (`runs._finish`; for v2, `v2.run._finish_v2`, with the Statement sources and Evidence Proposals too). Reason: a partial Dataset Version could be validated or published without positions.
- `ideology_app.pipeline` MUST depend on the `LLMProvider` protocol (`llm.base`), never on a concrete provider or `build_provider`; the CLI resolves the provider in `cli._provider`. Reason: the provider is configuration, and tests inject `FakeProvider`.
- Generation Mode MUST get its behaviour only from `pipeline.triggers.QUEUE_ON_SOURCE_CHANGE` (via `queues_on_source_change`); no `if mode == …` branches elsewhere. Elsewhere the mode is only recorded on the run. Reason: Generation Mode is configuration, not code branches scattered around (`AGENTS.md`).
- The live trigger (`queue_run_for_source_change`) MUST run in the same transaction as the Source Document it reacts to, and MUST NOT call an LLM, build a provider or read an API key; it only records a `queued` run. Reason: a document must never commit without its run (or vice versa), and adding a document must stay fast and free.
- Recorded LLM calls (`pipeline_run_calls`) MUST only be inserted (never updated or deleted by application code) and MUST be reused only by a run queued with an explicit `resumed_from_run_id` (set by `pipeline run --resume-from` or `--reuse-from`), only for an identical `request_hash`, and only after re-validating the stored output against the request schema. Reason: a resumed run must give exactly what the model answered, and a deliberate re-run must still regenerate (`pipeline-run-checkpoint`).
- Legacy pipeline only (v2: `constituency-selection-validation` owns selection): the final Statements MUST be chosen only by `pipeline.selection.select_statements`, before the Dataset Version is written: deterministic (no LLM, randomness or clock), every Party weighted the same, thresholds only from the run's `ValidationSettings`. Selected text and topic MUST be stored exactly as the provider returned them. Reason: leaving Statements out is a choice that must be reproducible, auditable and party-neutral (`pipeline-coverage-selection`).
- Legacy pipeline only (v2 has no Agenda; `statements-from-proposals`): the candidates sent to `generate_statements` MUST be chosen only by `pipeline.agenda.balance_candidates`: deterministic, the same quota for every Party, no Party label in the prompt. Reason: agenda balance must be reproducible and party-neutral (`pipeline-balanced-statements`).
- Legacy pipeline only (v2: see `proposal_positions` under Phase 4): `position_findings` MUST NOT allow stances inferred from general ideology or from silence; every stance cites a verbatim quote that contains the proposal. Reason: explicit-evidence rule (direction B, inferred stances, deferred by user decision 2026-10-22; `pipeline-balanced-statements`).
- `pipeline_runs.statement_selection` (the selection report, the `agenda` and, since `pipeline-verified-findings`, the `findings` extraction check) MUST be written only by `runs._finish`, in the commit that writes the Dataset Version, and MUST NOT be updated afterwards. Reason: it is the record of why each Statement was kept or left out, and of which findings were discarded.
- Legacy pipeline only: Party Position extraction MUST verify findings only through `validation.evidence_quotes` (`find_quote_miss`) and MUST NOT edit, trim or repair a quote. Reason: one matching rule with Validation, and AI output is never edited (a Statement's text changes only through a recorded Statement Rewording in a new run) (`pipeline-verified-findings`).
- Legacy pipeline only: the `party_positions` request MUST list every finding of the Party, verified or not; filtering happens on the reduce's output (a choice citing an unverifiable finding becomes `no stance`). Reason: recorded calls stay reusable (`--resume-from` / `--reuse-from`) (`pipeline-verified-findings`).
- Context notes MUST be stored exactly as the provider returned them and MUST NOT be written, backfilled or edited by application code or by hand; Dataset Versions created before `0014` keep NULL. A Statement Rewording never changes the Context Note (`statement-rewording`, R10). Reason: AI output is never edited (a Statement's text changes only through a recorded Statement Rewording in a new run), and Dataset Versions are immutable (`pipeline-statement-clarity-context`).
- Legacy pipeline only (a v2 run has no Anchors and records `anchor_dataset_version_id` NULL; `statements-from-proposals` S8): Anchors MUST come only from the Statements of the Election's Published Dataset Version (or, for a run with `resumed_from_run_id`, the anchor version that run recorded), resolved in `runs._start`, and MUST enter only as `generate_statements` prompt input, never as injected pool Statements or as a selection preference. Reason: every published Statement passes the same generation, selection and Validation, and replays stay reproducible (`pipeline-statement-clarity-context`).
- Legacy pipeline only (the v2 prompts have their own text in `pipeline/v2/prompts.py`): `StatementDraft`, `CandidateList` and `_COMMON_RULES` MUST NOT change without bumping `statement_candidates` (which voids every recorded candidate call). Reason: `--reuse-from` replays depend on it (`pipeline-statement-clarity-context`).
- Legacy pipeline only (v2: per-Constituency order and lengths, see Phase 4): Statement Selection (v3, `pipeline-statement-priority-tiers`) MUST write the selected Statements in priority order (most Parties in favour or against first) and MUST compute the Dataset Version's questionnaire lengths only from the run's `ValidationSettings` (`statement_count.expected_lengths`). `dataset_versions.questionnaire_lengths` MUST be written only by `runs._finish`, in the insert of the Dataset Version, and MUST NOT be updated or backfilled (versions created before `0015` keep NULL, read as their full length). Reason: a questionnaire of length N is always the first N Statements, and Dataset Versions are immutable.
- Request handlers (`api/`, `web.py`, `main.py`) MUST NOT queue or execute Pipeline Runs. Reason: nothing is ever generated per user; runs are queued by the Operator's `source add` and executed by `pipeline run` / `pipeline run-queued`.
- The topic catalog (names, display order, CIS mapping) MUST be edited only in `src/ideology_app/topic_catalog.py`, and `packages/core/src/domain/topic-catalog.generated.ts` MUST be regenerated from it (`python -m ideology_app.topic_catalog`), never edited by hand. Reason: Python and the web client must show the same categories in the same order (`tests/test_topic_catalog.py` checks it).
- Topic keys MUST NOT be renamed or removed while any Dataset Version uses them, and `prompts.Topic` / `TOPICS` MUST NOT be reordered for display (display order lives only in the catalog). Reason: stored Statements keep their key, and the `Topic` order is in the prompt text and schema, so reordering it changes request fingerprints and the Agenda tie-break (`topic-catalog`).

## Phase 4 (v2 pipeline)

- Any change to the `statement_drafts` or `proposal_positions` system text, template, `max_tokens` or schema (`pipeline/v2/prompts.py`) MUST bump that prompt's version in `V2_PROMPT_VERSIONS` and its fingerprint in `tests/test_v2_prompts.py`; the v2 prompts MUST NOT join the legacy `PROMPTS` / `PROMPT_VERSIONS`. Reason: a v2 run records the versions it used, and legacy fingerprints and recorded calls must stay unchanged (`statements-from-proposals`).
- No Party name, short name, file name or page MAY reach a v2 prompt: only Proposal text and tags, Statement texts, the category's Spanish name and the Context Note bounds. Reason: perceived bias; the UI and the pipeline treat all Parties identically.
- A v2 run MUST start only through `pipeline.v2.load_phase4` (in order: `require_phase4_ready`, the imported Election, `ledger_count_problems`, then `counted_proposals` per non-Excluded Party), from the CLI before queuing and again in `_start_v2`; a refusal creates no run (CLI) or fails the queued run (`phase 4 blocked: …`). Reason: a fabricated count, a pending conflict or a stale ledger must never reach Statement generation (`ingestion-ledger`, `proposal-conflicts`).
- `statement_proposals` and `party_position_proposals` MUST be written only by `pipeline.v2.run._finish_v2`, in the commit that writes the Dataset Version, and MUST only be inserted; Statement sources and Evidence MUST come only from `counted_proposals`. Rank 1 of a Position's Evidence MUST always be mirrored into its `evidence_*` columns (the Proposal text exactly, its page, its Source Document row and that row's URL). Reason: Dataset Versions are immutable; the mirror keeps check 2 and the v1 API code working unchanged.
- `model_generation` MUST be set when a run is queued and copied into its Dataset Version at insert, and MUST NOT be updated. Reason: it decides the checks, the publish rule and how readers interpret immutable rows.
- The legacy `pipeline run` MUST NOT run on an Election with candidatures (`queue_run` refuses; `_start` fails an already queued one), and the live trigger MUST NOT queue a run for such an Election in any mode. Reason: the legacy run reads every Party and ignores Proposals, conflicts and Excluded Parties (`statements-from-proposals` S10, S11).
- A passed v2 run MUST be published by the same rule as a legacy one (`publishing.PUBLISH_ON_PASS[v2]` is `True` since `constituency-selection-validation`, K12): run-id order, superseding the Election's Published version of either generation; a v2 run with no available Constituency MUST fail (`constituency_availability`, K8) and so is never published. Reason: an unusable version must never supersede a working one, and publishing follows one rule.
- The per-Constituency rows of a v2 Dataset Version (availability and reason, n(c), offered lengths, the ranked Statements) MUST be computed only by `constituency_rules` through `pipeline.v2.selection.select_constituencies`, before the write: deterministic (no LLM, randomness or clock, no iteration over unordered sets), every Party treated the same, thresholds only from the run's `ValidationSettings` (topic share) and `ConstituencySettings` (minimums). Reason: which Statements a Voter sees must be reproducible, auditable and party-neutral (`constituency-selection-validation`).
- `dataset_version_constituencies`, `dataset_version_candidatures` and `constituency_statements` MUST be written only by `pipeline.v2.run._finish_v2`, in the commit that writes the Dataset Version, and MUST only be inserted; legacy Dataset Versions have no rows there (`db check` reports any). Reason: Dataset Versions are immutable.
- A Constituency below a minimum (`VALIDATION_V2_MIN_STATEMENTS`, `VALIDATION_V2_MIN_PARTY_SIDES`) or with fewer than two non-Excluded Parties MUST be stored unavailable with its reason and MUST NOT fail the run; the four `constituency_*` checks only confirm the stored rows. Reason: user decision 2026-11-24 (a Constituency is shown unavailable, the run goes on).
- Readers of a v2 Party Position per Constituency (selection, Validation, the v2 read model `api/queries_v2.py`) MUST apply S5 only through `constituency_rules.effective_value`, and a reader that shows a Position's Evidence in a Constituency MUST pick it only with `constituency_rules.counting_evidence` (`effective_value` is defined through it). Reason: one rule, so the Questionnaire, its checks and the served values and Evidence never disagree.
- `dataset_version_proposals` (the frozen counted Proposals of each non-Excluded Party, migration `0021`) MUST be written only by `pipeline.v2.run._finish_v2` from `phase4.parties`, in the commit that writes the Dataset Version, and MUST only be inserted; legacy Dataset Versions have no rows there, and every Evidence row of a v2 version MUST be frozen there for the same Party with the same Constituencies (`db check` reports both). Readers of a Dataset Version's Proposals (the public API) MUST read them only from this table, never from `counted_proposals`, the Ingestion Ledger or the bundle files. Reason: Dataset Versions are immutable and K9 forbids reading the ledger for a written version (`public-dataset-api-v2` A8).
- A written v2 Statement MUST NOT be dropped because it is valid in no available Constituency; it keeps its Positions and Evidence and gets no `constituency_statements` row (K7). Reason: AI output stays inspectable, and the stored pool must not depend on the thresholds of one replay.
- `statement_rewordings` MUST be written only by `pipeline.v2.run._finish_v2`, in the commit that writes the Dataset Version, and MUST only be inserted; legacy Dataset Versions have no rows there (`db check` reports any). Reason: Dataset Versions are immutable, and the AI text of a reworded Statement must stay inspectable (`statement-rewording`).
- Statement Rewordings MUST come only from the bundle's `statement-rewordings.toml`, read through `pipeline.v2.rewording.read_rewordings` (by the CLI before queuing and again in `_start_v2`), MUST be applied only after `assign_positions` (and before Constituency Selection), and only with an `equivalent` `statement_rewording_check` verdict; a rejected, duplicate or not-found entry MUST NOT fail the run and MUST be listed in `statement_selection["rewordings"]`. No flag, override or edit of a stored row MAY change a Statement's text. Reason: Positions and Evidence stay those computed on the AI text (a `--reuse-from` replay reuses every draft and position call), and a rejected rewording is reported, not fatal (user decision 2026-11-24).
- The Operator's `reason` MUST NOT reach any prompt: `statement_rewording_check` sees only the AI text, its Context Note and the new text (no Party, file or page). Reason: the reason argues for acceptance and would bias the judge.
- Any change to the `statement_rewording_check` system text, template, `max_tokens` or schema MUST bump its version in `V2_PROMPT_VERSIONS` and its fingerprint in `tests/test_v2_prompts.py`, like the other v2 prompts. Reason: a run records the versions it used, and a bump voids the recorded verdicts.
- Readers serving Voters (the API, today `/api/v1`, and `public-dataset-api-v2`) MUST serve only `statements.text`: never `ai_text`, the reason, the explanation or any marker that a Statement was reworded. Reason: user decision 2026-11-24 (Voters see only the final text; `/metodologia` explains that the authors may reword confusing Statements).

## Validation

- Validation checks MUST be pure functions of `ValidationInput` (no database, LLM, network or clock). Reason: checks are unit-tested on plain data and give the same result on every re-run; anything a check needs is loaded once in `validation.base.load_input`.
- Validation results and report entries MUST be written only by `pipeline.runs.validate_run`, in the same commit as the run's `passed` / `failed` status, and MUST NOT be updated or deleted. Reason: the report is the durable record of why a run passed or failed.
- Evidence quote matching and Statement duplicate detection MUST go through `validation.evidence_quotes.normalize_for_match`. Reason: one matching rule for Validation and anything later that shows whether a quote was found.
- Validation thresholds MUST come from `config.ValidationSettings` (read from the environment by `config.validation_settings()` and passed into `ValidationInput.settings`), never from literals inside a check. Reason: thresholds are configuration, and checks stay pure and testable at any threshold.
- Legacy pipeline only (v2: a Party below `VALIDATION_V2_MIN_PARTY_SIDES` makes its Constituency unavailable, see Phase 4): a Party below the coverage threshold MUST fail the whole run and MUST NOT be excluded from a Dataset Version (a v2 Party is Excluded only in the Ingestion Ledger, `ingestion-ledger`; the `too_few_proposals` side follows only from the ledger counts that phase 3 records, `proposal-extraction`). Coverage counts only sided Positions (+1/+2 or −1/−2; not 0, not `no stance`; `pipeline-statement-priority-tiers`). Reason: excluding a Party silently changes the Voter's ballot, the UI treats all Parties identically, and AI output is never edited.
- Legacy pipeline only (v2 uses topic deferral in the per-Constituency order and records each length's topic share in the report): coverage and topic spread MUST be checked on every offered questionnaire length (each prefix of the Dataset Version), and a failing length MUST fail the whole run; lengths MUST NOT be dropped, and shorter lengths MUST NOT get a lower threshold, to make a run pass. Reason: user decision 2026-11-21 (strict); a shorter questionnaire must be as balanced as the full one, and tuning is a deliberate settings change replayed with `--reuse-from` (`pipeline-statement-priority-tiers`).
- Legacy pipeline only (v2: validity is per Constituency, and a Statement valid nowhere is kept, see Phase 4): a Statement that does not separate the Parties (since `pipeline-statement-priority-tiers`: no Party in favour (+1/+2) or none against (−1/−2); 0 and `no stance` count on neither side) MUST fail the whole run and MUST NOT be dropped from a Dataset Version once written (the pre-write selection is the only place Statements are left out). Reason: Dataset Versions are immutable, AI output is never edited, and the run is the unit of publication.
- A Statement set whose count is outside the configured range (legacy pipeline only; v2 has no count range), that puts more than the configured share on one topic (legacy pipeline only), that contains duplicate Statements (same text after `normalize_for_match`), or that has a Statement whose context note is missing, out of the configured length range or uses a configured evaluative word (check `context_note`, `pipeline-statement-clarity-context`) MUST fail the whole run; the Statements of a written Dataset Version MUST NOT be dropped, deduplicated or reordered to make it pass (the pre-write selection is the only place Statements are left out). Reason: the same as for separation; the operator re-runs or changes a threshold deliberately instead.
- A Dataset Version's status (and an Election's `draft` → `active`) MUST change only in `pipeline.publishing.publish_dataset_version`, called from `validate_run`'s `passed` path in the same commit as the Validation results; checks MUST NOT change it. The only transitions are `candidate → published` and `published → superseded`; a version that is not `candidate` is never published again. Reason: publishing and superseding are one transition with its own rules (at most one Published version per Election, publish order = Pipeline Run id).
- The partial unique index `uq_dataset_versions_published_election_id` (`dataset_versions (election_id) WHERE status = 'published'`, migration `0007`) MUST NOT be dropped, and any future batch migration of `dataset_versions` MUST keep it with its WHERE clause (autogenerate and `alembic check` do not compare the WHERE clause; `tests/test_migrations.py` checks `sqlite_master`). Reason: it is the database backstop for one Published version per Election.
- When superseding, the old Published version MUST be flushed as `superseded` before the new one is set `published`. Reason: the unit of work orders UPDATEs by primary key, so a single flush can hit the partial index.
- `pipeline_runs.validation_settings` MUST be written only by `pipeline.runs.validate_run`, in the commit that stores the run's Validation results (on `passed` and `failed`), and MUST NOT be updated afterwards. Reason: it is the record of the thresholds that produced those results; a later change would make the report lie.
- `ideology pipeline report` (`pipeline.reports`) MUST stay read-only: no writes, no options that change state. Reason: AI output is never edited (a Statement's text changes only through a recorded Statement Rewording in a new run), and the report is an observability view.

## Public API

- `/api/` routes MUST be `GET`-only and read-only (SELECT only; the request Session is never committed) and MUST NOT accept Answers (no query or body parameters). Reason: voter answers never reach the server, and the API is a public read surface.
- `GET /api/v1/legal-notice` (`getLegalNotice`, legal-privacy-page) is part of this read-only surface: no parameter, no Session, it serves only `app.state.legal_notice` (the parsed `LEGAL_*` settings). It is not a write.
- `GET /api/v1/donation` (`getDonation`, donate-buymeacoffee) is part of the same read-only surface: no parameter, no Session, it serves only `app.state.donation_url` (the parsed `DONATION_URL`).
- The single exception is `POST /api/v1/feedback` (`api/feedback_routes.py`, `feedback_router`): it writes only the feedback store, never the shared database Engine, and its body is limited to `message`, `origin` and `website` (any other key is refused with 422). Any other write route needs its own spec and a change to this rule. Reason: anonymous feedback is the only Voter-written data the server keeps (`feedback-api`).
- Operator routes live under `/admin/api/v1` (`api/admin_routes.py`, `admin_router`), outside the public `/api/` prefix, MUST NOT appear in the public OpenAPI (`include_in_schema=False`), and every one of them except sign-in (`POST /admin/api/v1/session`) MUST need a session. Reason: the public API stays a read-only, anonymous surface (`feedback-admin`).
- The API MUST NOT serve `candidate` Dataset Versions; an unknown and a `candidate` id MUST get the same `404 dataset_version_not_found`. Reason: only versions that passed Validation are published.
- A `DatasetVersion` response body MUST NOT contain mutable fields (status, the Published pointer). Reason: it is cached `public, max-age=86400, immutable`; the pointer lives in `Election.published_dataset_version_id`.
- A Party Position's `value` MUST come from `PartyPosition.engine_value`. Reason: one mapping to what the `packages/core` match-score engine consumes.
- `DatasetVersion.questionnaire_lengths` is part of the immutable body: the stored lengths, or `[statement count]` when NULL (`pipeline-statement-priority-tiers`).
- `/api/v1` changes MUST be additive; a breaking change needs `/api/v2`. Reason: clients and old Share Links depend on the contract.
- A v2 Dataset Version MUST NOT be served in the legacy `DatasetVersion` shape: `getDatasetVersion` and `getPublishedDatasetVersion` answer `404 dataset_version_is_v2`, and the Constituency routes answer `404 dataset_version_is_legacy` for a legacy version. Legacy bodies (Dataset Versions 1–5) MUST stay byte-identical. Reason: a v2 version has no national questionnaire, and today's clients would misread one (`public-dataset-api-v2` A2).
- The Constituency routes (`queries_v2`) MUST take only path parameters (`code` `^[0-9]{2}$`, `category` a `TOPIC_CATALOG` key in the path, never `?category=`), MUST list Excluded Parties only in `excluded_parties` (never in `parties` or the Proposals route), and MUST order and shape every Party the same. Reason: no Answers reach the server, and the UI treats all Parties identically.

## Client-side Matching

- The Match Score MUST be computed only by `packages/core/src/domain/match-score.ts` in the client. The server MUST NOT get an endpoint that receives Answers. Reason: the invariant that voter answers are never stored or sent to the server.
- `packages/core` MUST NOT import React, DOM or platform APIs, and `match-score.ts` MUST have no imports and use no globals beyond the language built-ins. Reason: the core is shared by the web and (later) mobile clients and tested under Node.
- Client code MUST NOT put Answers (including Important flags) in any request (path, query string, body or headers); only the URL fragment carries them (Share Links). Reason: the invariant above, and server access logs record full request lines.
- The feedback POST (`sendFeedback` in `createPublicApiClient`) is the only request that carries free text, and it carries no Answers: `sendFeedback` sends only `message`, `origin` and a non-empty `website`, never an Election, Dataset Version or Answers. Reason: the invariant above; the Voter's own words are the only thing they choose to send (`feedback-api`).

- Share Link payloads MUST be produced only by `encodeShareLink` and read only by `decodeShareLink` (`packages/core/src/infrastructure/share-link/share-link-codec.ts`). Reason: one strict, tested format and one place to audit what a link carries.

A retired marker MUST be recognised and opened as the outdated-version message (`outdated_version` → `outdated`), never a generic error. `v1` (five-point scale plus skip) was retired on 2026-11-21 by `three-option-scale`. Reason: old links stay valid for the old, immutable Dataset Versions they pin, and a retired link must still explain itself.

Until `questionnaire-length-and-context` relaxes `restoreQuestionnaire`, only full-length links are produced or accepted. Reason: Statements are stored in priority order, so a prefix is the same layout (`pipeline-statement-priority-tiers`).
- Client code MUST NOT write a Share Link or Answers into the current page URL, history or storage; only the clipboard or the on-screen fallback field may hold them. Reason: shared devices and browser history must not keep answers.

The end screen and the shared result MUST both get their ranking and breakdown from `buildResults` (`packages/core/src/domain/results.ts`). Reason: one auditable ordering rule, identical treatment of Parties, and a shared link that shows exactly what the end screen showed.
- A Share Link MUST be opened only through `openShareLink` (`packages/core/src/application/open-share-link.ts`), and the shared page MUST render a result only from its `ready` value (no partial result on any error). The shared page MUST NOT rewrite, strip, store or copy the fragment (no `history.*`, storage or logging); it reads it only through the router location. Reason: one tested path from untrusted fragment to screen, and the answers stay only in the link the opener already has.
- AI-generated text (Statements, Evidence quotes) MUST be rendered as text, never through `dangerouslySetInnerHTML`; Evidence links MUST come from `evidenceHref` (`packages/core/src/domain/breakdown.ts`, http/https only) and open with `target="_blank" rel="noopener noreferrer"`. Reason: LLM output and Operator URLs are untrusted, and a same-tab navigation loses the Answers.
- The "Comparte IdeologiApp" share targets MUST share only `appHomeUrl(location.origin)`, built only by `apps/web/src/features/share/app-share-links.ts` (never a path, query, fragment, Dataset Version id or Answers). Third-party share targets MUST be plain Voter-started navigations (links or `navigator.share`), with no SDK, script, image, iframe or preconnect from another origin. Reason: answers never leave the browser, and the page loads nothing from another origin.
- Client code MUST reach the public API only through the `packages/core` client (`createPublicApiClient`); components MUST NOT call `fetch` (only `apps/web/src/main.tsx` passes the browser `fetch` in). The Operator admin page is the one other entry: `apps/web/src/admin/main.tsx` passes `fetch` only to `createAdminApiClient`, and Voter code MUST NOT import anything from `apps/web/src/admin/` (`admin-isolation.test.tsx`). Reason: one place that checks the API contract and maps keys, one place to audit that no request carries Answers, and no admin code in the Voter bundle.
